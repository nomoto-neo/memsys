# パッケージ化の作業計画

ネオビットフレームワーク（`packages/neobit/core/`）を、見本のサイト（memsys）から切り離して配れる形にするための計画。作業の途中で経緯を忘れても、ここを読めば続きから始められるように書く。

作業のブランチは `packaging`。段階が1つ済むたびに、この文書の「状態」の列を書き換える。

## 目指す形

まっさらな Laravel のプロジェクトに `neobit/core` を入れるだけで、フレームワークの部品が動く。プロジェクトは、変えたい所だけを自分の側に書いて上書きする。

今は、フレームワークが見本のサイトの側に置いたファイル（設定・メールのテンプレート・JavaScript）を前提にしている所が残っている。それを無くすのが、残りの作業の中心になる。

## 決まっている方針

2026-10-14 に決めたもの。

| 対象 | 方針 |
|---|---|
| 設定の値 | パッケージの側に既定の値を持たせる。プロジェクトは Laravel の仕組みで上書きする |
| プロジェクトの設定ファイル | 既定と同じ値は、頭に `//` を付けて見本として見せる。変えた値だけが生きた行になる。パッケージは、既定の値（`config/`）とは別に、値をコメントにした写す元（`stubs/config/`）を持つ |
| メールのテンプレート | 設定と同じ。パッケージの側に既定のテンプレートを持たせ、プロジェクトが上書きする |
| JavaScript・CSS など | パッケージの中に置く。プロジェクトの `vite.config.js` に、`vendor/neobit/` から始まるパスを直接書く |

### 段階1　設定の既定の値

済み。フレームワークが読む設定の、既定の値の置き場所は次のとおり。

| 設定のキー | 読んでいる部品 | 既定の値の置き場所 |
|---|---|---|
| `upload.*`（5つ） | `AjaxFileUpload`・`CsvReader`・`CsvImport` | パッケージの `config/upload.php` |
| `cleanup.operation_log_days`・`failed_job_days`・`tasks` | `TemporaryDataCleaner` | パッケージの `config/cleanup.php` |
| `neobit.admin_requests_per_minute`・`admin_requests_exceeded_message` | `AdminRequestLimit` | パッケージの `config/neobit.php` |
| `neobit.operation_report_to`・`operation_report_thresholds` | `ReportOperationLogs`・`OperationLogReport` | パッケージの `config/neobit.php` |
| `app.site_name` | 画面2つ・`ErrorNotifyHandler`・`ReportOperationLogs`・`TeamInvitationManager` | プロジェクトの `config/app.php` |
| `services.turnstile.*` | `SpamGuard`・`_spam_guard.blade.php` | プロジェクトの `config/services.php` |
| `login.{種類の名前}.legacy_passwords` | `LegacyPasswordUserProvider` | プロジェクトの `config/login.php` |

- パッケージの `config/` に置いたファイルを、サービスプロバイダーが `mergeConfigFrom()` で既定の値にする。プロジェクトの `config/` に同じ名前のファイルで書いたキーが優先する
- 管理画面の回数の制限と、操作ログの報告の設定は、`config/app.php`・`config/logging.php` から `neobit.*` へ移した。フレームワークだけが読む値で、Laravel 自身の設定ファイルに間借りしたままだと、パッケージが既定の値を持てないため
- `app.site_name`・`services.turnstile.*`・`login.*` は動かしていない。`site_name` はプロジェクトの画面も読み、`turnstile` は Laravel の習わしどおりの場所にあり、`login` は種類の名前がプロジェクトごとに違う。どれも、無ければ空として動く
- 期限の切れた招待の片付けは、`TemporaryDataCleaner` が自分で呼ぶ。プロジェクトの `cleanup.tasks` には、業務のデータの片付けだけを書く
- `php artisan vendor:publish --tag=neobit-config` で、設定の見本をプロジェクトの `config/` へ写せる。写す元は段階1-2

後の段階でも気を付けること。

- `mergeConfigFrom()` が混ぜるのは、いちばん上の階層のキーだけ。配列の値（`upload.image_types`、`cleanup.tasks`、`neobit.operation_report_thresholds`）は、プロジェクトが書くと丸ごと置き換わる。中の1つだけを変えるつもりで一部だけ書くと、残りが消える

### 段階1-2　設定の写す元

済み。2026-10-14 に決めた形。

| 役割 | 置き場所 | 中身 | 使われ方 |
|---|---|---|---|
| 既定の値 | パッケージの `config/upload.php` など | 値が生きている | `mergeConfigFrom()` が読む |
| 写す元 | パッケージの `stubs/config/upload.php` など | 値に `//` を付けた見本 | `vendor:publish --tag=neobit-config` がプロジェクトの `config/` へ写す |

- 見本のサイトの `config/upload.php`・`config/cleanup.php`・`config/neobit.php` も、既定と同じ値をコメントにしてある
- 既定の値と写す元は別のファイルなので、ずれる。写す元の `//` を外した結果が既定の値と一致することを、テスト（`ConfigStubTest`）で確かめている
- `neobit` の設定のキーは、全部に既定の値がある。`code_table_db`・`code_table_method` は空の配列、`operation_log_actions` はフレームワークの操作の種類だけ、`operation_log_route` は `null`
- 写す元では、値の行を「`//` の後ろが `'`・`[`・`]`・`\` で始まる行」と決めている。テストがこの決まりで `//` を外すので、説明のコメントをこれらの文字で始めない

### 段階2　メールのテンプレート

済み。フレームワークが送るメールの既定のテンプレートは、パッケージの `resources/mail-templates/` にある。

| テンプレート | 送る部品 | 名前の決まり方 |
|---|---|---|
| `error_notify` | `ErrorNotifyHandler` | 固定 |
| `operation_log_report` | `ReportOperationLogs` | 固定 |
| `verification_code` | `LoginVerificationCode` | ログインする人の種類ごと |
| `password_changed` | `PasswordChange` | 同じ |
| `profile_changed` | `LoginProfileNotice` | 同じ |
| `invitation` | `TeamInvitationManager` | 同じ |

- `MailTemplate` は、プロジェクトの `resources/mail-templates/` を先に探し、無ければパッケージのものを使う
- 種類ごとのテンプレートは、3段で探す。プロジェクトの `member_verification_code`、プロジェクトの `verification_code`、パッケージの `verification_code` の順。プロジェクトに種類の名前を付けない名前で置くと、全部の種類に共通の文面になる
- 探す名前は、`TemplatedMail` の名前に配列で渡す。部品が `[種類の名前を付けた名前, 付けない名前]` を書く。`LoginAccount` にメソッドは足していない
- `php artisan vendor:publish --tag=neobit-mail-templates` で、既定のテンプレートをプロジェクトへ写せる
- 既定のテンプレートは、部品が渡す値だけで展開できる。プロジェクトのルート（お問い合わせの画面など）には頼らない。本人以外がパスワードを変えたときの文面には、変えた人の氏名を出さない。会員宛てのメールにスタッフの氏名が出るため
- 件名の頭は `【サイトの名前】` にそろえた。確認コード・パスワードの変更・登録情報の変更の部品が、`site_name` を渡す。`SITE_NAME` が空のサイトでは `【】` になるので、プロジェクトの側でテンプレートを置いて書き換えてもらう
- 見本のサイトは、種類ごとのテンプレート（`member_…`・`company_user_…`・`staff_…`）を残し、件名だけ同じ形にそろえた。`error_notify` と `operation_log_report` は消して、パッケージの既定を使う

### 段階4-3　ほかのテーブルから作るコード表

済み。2026-10-15 に足した段階。スタッフの一覧のように、ほかのテーブルから作るコード表を、ほかのコード表と同じヘルパー（`code_table()`・`code_label()` など）で引けるようにした。

| 設定 | 中身 |
|---|---|
| `code_table_db` | DB の `code_tables` テーブルのコード表。コード名 => 名前と「コード値を固定するか」。もとの `code_tables` から改めた。ヘルパーの `code_table()` と1文字違いで紛らわしかったため |
| `code_table_method` | プログラムで作るコード表。コード名 => `[クラス, 静的メソッドの名前]` |
| `code_table_enum_namespaces` | 列挙型のコード表を探す名前空間。値の中身がほかの2つと違うので、名前はそろえずに残した |

- 設定には関数ではなく、クラスとメソッドの名前を書く。`config:cache` で固められるようにするため。メソッドの名前まで書くので、モデルに静的なメソッドを書くだけで済む
- モデルは無いメソッドの呼び出しもクエリへ回すので、`is_callable()` では見分けられない。メソッドがあって public かつ static であることを、`CodeTable` が確かめてから呼ぶ
- 論理削除した行を、名前には出し、選択肢には出さないときは、メソッドを分けてコード表を2つにする。見本のサイトの `staff`（削除したスタッフも含む）と `active_staff`（今いるスタッフだけ）
- `code_table_merge` は無くした。使っていたのは操作ログの操作のコード表だけで、`operation_log_actions` と同じ一覧を二重に書いていた。今は `CodeTable` が、`OperationLog::actionOptions()` を自分で持つメソッドのコード表として、設定に書かなくても先に見る。設定の既定の値に入れないのは、`mergeConfigFrom()` が1段目しか混ぜず、プロジェクトが `code_table_method` を書くと消えてしまうため

### 段階4-4　アップロードの保存先の規則

済み。2026-10-15 に足した段階。保存先のディレクトリの組み立て方は、プロジェクトによって希望が違うので、差し替えられるようにした。

- 規則は、`UploadDirectoryRule` を実装したクラスが決める。メソッドの名前は `directory()` に決めた。1つのサイトで使う規則は1つなので、名前を自由にすると、かえってエンジニアが迷うため
- 使うクラスは `config('upload.directory_rule')` に書く。既定は `DefaultUploadDirectory`（`news/000/000012`）で、元の `UploadFilePath::directory()` の規則をそのまま移した
- `UploadFilePath::directory()` は、設定のクラスを呼んで確かめるだけにした。保存・URL・削除・非公開のファイルの配信は、どれもここを通るので、呼ぶ側は変えていない
- 規則が受け取るのは、モデルのクラス名と id だけ。レコードの中身（登録した日など）は使えない
- 設定のクラスが約束を実装していないときと、`..` や先頭・末尾の `/` を含むディレクトリを返したときは、例外にする

### 段階4-5　名前の総点検

2026-10-15 に足した段階。メソッド・定数・設定のキーなどの名前を変えると、配った後は全案件のコードを直す変更になる。版を出す前に、案件が頼る名前を全部見直して固める。

名前の一覧は `docs/neobit-framework-names.md` にある。コードから機械的に集めたもので、「メモ」の列に、集めたときに気付いた見直しの候補を書いてある。

進め方。

1. 一覧の種類ごとに、気になる名前と案を出して決める
2. 決まった分を種類ごとに直して、コミットする
3. 一覧を、直した後の名前に書き換える。見直しが済んだ後も、「案件が頼ってよい名前の一覧」として残す

見直す観点。2026-10-15 までの見直しで出てきたもの。

- 同じ種類のものは、同じ形の名前にそろえる（「〜Values」「〜PageValues」など）
- 名前と働きが食い違わない（`inputValues()` は入力値を扱うものと紛れたので、`pickValues()` にした）
- PHP や Laravel の慣習と、逆の意味に見えない（`from〜` は静的な作り方、`filter` は外すこと、`path` はディレクトリ）
- 1文字違いのような、紛らわしい組を作らない（設定の `code_tables` とヘルパーの `code_table()`）
- 案件がフレームワークのために用意するクラスは、名前を `App` で始める（`AppOperationLogAction`・`AppOperationLogModel` など）。外れるときは、作る前に相談する。2026-10-16 に決めた

|---|---|
| 1. コントローラーが書くメソッド | 未 |
| 2. コントローラーが呼ぶメソッド | 未 |
| 3. コントローラーが書く定数 | 未 |
| 4. モデルが書くもの | 未 |
| 5. インターフェース・トレイト・列挙型 | 未 |
| 6. 案件が呼ぶクラス | 未 |
| 7. ヘルパー | 未 |
| 8. 設定のキー | 未 |
| 9. 画面と変数 | 未 |

| 11. メールのテンプレートと変数 | 未 |

### 段階4-6　IPブロック管理

済み。2026-10-15 に足した段階。不正な URL を続けて叩く BOT を、PHP の側で止める仕組み。Cloudflare などの WAF や fail2ban を入れられない環境での自衛のため。今までは、アクセスログから IP を調べて `.htaccess` に手で足すしかなかった。

ルートを通るフレームワークなので、どの URL へのアクセスも、全体のミドルウェアを必ず通る。ルートの無い URL（`/.env`・`/wp-login.php` など）も、ルートを探す前に通る。そこで止めている IP なら 404 を返す。403 にしないのは、止められていることを相手に気付かせないため。画面も、ルートの無い URL を開いたときと同じ 404 の画面にする。ルートの無い URL への 404 と同じ重さなので、負荷は変わらない。Apache が PHP を通さずに返すファイル（画像・CSS など）は止まらないが、攻撃の狙いにはなりにくいので許容する。

**設定**（`config/neobit.php`。案件で上書きできる）

| キー | 既定 | 中身 |
|---|---|---|
| `ip_block_auto` | `true` | 自動で止めるか。`false` なら手動の登録だけ |
| `ip_block_watch_minutes` | `10` | 数える時間（分） |
| `ip_block_watch_count` | `30` | その時間に、応答が 404・405 になったアクセスが何回あったら止めるか |
| `ip_block_hours` | `24` | 自動で止める時間 |

ふつうの人が10分に30回も存在しないページを開くことは無く、BOT は数秒で数十回叩くので、その間に置いた。

**動き**

1. 全体のミドルウェア（`RejectBlockedIp`）が最初に、止めている IP かを見る。判定はキャッシュで行い、DB は読まない。登録・解除のときに、キャッシュを作り直す
2. 応答が 404・405 になったアクセスを、IP ごとにキャッシュで数える
3. 目安を超えたら、`ip_blocks` に「自動」として登録する。IPv4 は1つ、IPv6 は `/64` 単位
4. 期限が来たら止めるのをやめる。期限の過ぎた行は、`TemporaryDataCleaner` が消す
5. 手動の登録は、IP 1つでも、まとまり（`/24` など）でもよい。判定は `AllowedIps` の仕組みを使い回す

止めない IP。`ADMIN_ALLOWED_IPS`・`SITE_ALLOWED_IPS` で許可している IP は、自動でも手動でも止めない。管理画面では、今の自分の IP も登録できないようにする。管理者が自分を止めないようにするため。

**管理画面「IPブロック管理」**（管理者だけ）

- 止めている IP の一覧。IP・手動か自動か・理由・回数・止めた日時・期限・登録したスタッフ
- 手動の登録（期限なしも選べる）・解除・期限の変更
- 一覧と登録の欄に、実際に止まる範囲（`203.0.113.0 ～ 203.0.113.255`）を出す。一覧はサーバーが計算し、登録の欄は `ip_block.js` が入力に合わせて出す
- 広すぎるまとまり（IPv4 は `/16`、IPv6 は `/32` より広いもの）は登録させない。関係の無い人まで大勢止めるため
- 画面とコントローラー（`IpBlockController`）はフレームワークに置く。ルートは案件が書く。機能を使うかどうかは案件ごとに決めるため。項目見出し一覧と同じ形

**記録と報告**

- 登録・解除・自動で止めたことを、操作ログに残す。操作の種類を2つ（`ip_block`・`ip_unblock`）足す。操作の対象のモデルは持たせない。フレームワークのモデルを対象にすると、案件の `enforceMorphMap()` に載せる手間が要るため
- 毎朝の操作ログの報告メールの「気になる点」に、前の日に自動で止めた IP を載せる。テンプレートは変えていない
- 部品の名前は、判定と登録をする部品を `IpBlocker`、ミドルウェアを `RejectBlockedIp` にした。テーブルのモデル `IpBlock` と同じ名前を避け、独立した部品の名前を「〜er」にそろえるため

**気を付けること**

- 手前にプロキシがある環境で `TRUSTED_PROXIES` が正しくないと、全員が同じ IP に見える。その IP を止めると、サイト全体が止まる
- 携帯電話の回線や会社の回線は、多くの人が同じ IP を使う。自動で止める時間を長くしすぎない
- IP を次々に変えて来る攻撃は止めきれない。WAF の領域

|---|---|

**301 リダイレクトの管理**（この段階の最後の機能）

`.htaccess` に書くリダイレクトは、書き方の誤りや、決まりの順番（どれが先に当たるか）の勘違いで、意図した動作にならないことが多い。そこで、管理画面から登録し、登録した内容を確かめられるようにする。

- 登録：古い URL（パス）・新しい URL・種類（301 か 302）・有効か。管理画面の一覧で、追加・編集・削除する
- 動かす場所：Laravel のミドルウェアで、ルートより前に当てる。`.htaccess` の書き換えはしない（apache にファイルを書かせないため）。当てる順番は1つの決まり（完全に一致するものだけ、など）にして、順番の勘違いが起きない形にする
- 登録のときの確かめ（案）：
  - 古い URL の形（`/` から始まるパス。クエリや `#` の扱い）
  - 同じ古い URL の二重の登録
  - 古い URL と新しい URL が同じ（自分へのリダイレクト）
  - リダイレクトの輪（A → B → A）と、つながり（A → B → C。A → C にまとめるよう案内する）
  - 古い URL が、今ある画面や記事の URL と重なる（リダイレクトが先に当たり、画面が開けなくなる）
  - 新しい URL が、サイトの中で開けるか（存在しない画面や記事を指していないか）
- 試す道具：URL を入れると、どのリダイレクトに当たり、最後にどこへ着くかを画面で見せる
- 当たった回数と最後に当たった日を記録して、使われなくなったリダイレクトを片付けられるようにする（案）

### 段階4-11　改ざん監視

済み（2026-10-27。`FileWatcher`・`app:watch-files`・メールのテンプレート `file_watch_alert`・設定の `file_watch`。設計は `docs/file-watch-spec.md`）。2026-10-27 に足した段階。このフレームワークは、IPブロック・操作ログ・怪しい操作やエラーの通知のように、サイトの運営者が自分で守る機能を持つことを主な目的にしている。改ざん監視は、入口で止めきれずに書き換えられたときに、侵入者が仕組みに気付く前に知らせる役目。

決まっている方針。

| 項目 | 決まったこと |
|---|---|
| 知らせ方 | 通知のメールだけ。管理画面には出さない（改ざんされたら、管理画面を見て運用する状況ではないため） |
| 何を知らせるか | 通常の運用では変わらないファイルが変わった・増えた・消えたときに、ファイルの一覧を作ってメールで送る。アップロードの置き場所（`storage/app`・`public/storage`）に `.php` などが現れたときも、すぐ送る |
| 間隔 | 5分ごと。判断はファイルの ctime で行うので、間隔で変わるのは知らせるまでの速さと、鍵の更新を見落とす幅だけ |
| 動かす権限 | コードを更新する利用者（webapp）の crontab から、コマンドを直接動かす。Laravel のスケジューラー（apache の cron）には入れない。基準を書き換えられるのはこの利用者だけにし、Web の側から侵入した攻撃者（apache の権限）は読むことしかできないようにするため |
| 基準（ハッシュ値の一覧）の置き場所 | `bootstrap/cache`（webapp だけが書け、apache は読むだけ）。最初の基準は、サーバーでコマンドを1回実行して作る。管理画面から基準を作り直す仕組みは作らない（管理画面を乗っ取られると、改ざんを正しい状態として登録されるため） |
| 速さ | 毎回は stat（ctime と大きさ）だけを比べ、違いのあったファイルだけハッシュ値を取り直す。1日1回、全部のハッシュ値を比べ直す。時刻はファイルの mtime ではなく ctime と、監視が気付いた時刻を使う（mtime は `touch -d` で書き換えられるため） |
| 通常の更新の見分け方 | 鍵のファイルの更新の前後に変わったファイルは、通常のサイトの更新とみなし、通知せずに基準を更新する。判断はファイルごとに、鍵とそれぞれのファイルの ctime で行い、監視の回った時刻は使わない。監視は、気付いた鍵の ctime を全部履歴に残す |
| 更新の期間 | 見えた鍵どうしの間が30分以内なら、一続きの更新の期間にまとめる。期間は、最初の鍵の20分前から最後の鍵の15分後まで。前の余白を「15分＋監視の間隔」にするのは、監視の1回の間に鍵が2度更新されて前の更新が見えないとき（最大で間隔の分）を吸収するため。続けて何度も更新しても、途中の鍵がいくつ見えなくても、期間の中のファイルは通常の更新になる |
| 判断を待つ | 鍵の無い変化に気付いたら、そのファイルの ctime から15分たつまで「保留」にして待ち、その間に鍵が更新されれば通常の更新、されなければ通知する（送る順番で、鍵が後から届くことがあるため）。通知は変化から最大でおよそ20分（待つ15分と、監視の間隔の5分）遅れる |
| 記録 | 判断の付いたファイルは、その回のうちに基準へ取り込む。基準・保留・鍵の履歴を `bootstrap/cache` に置く。通常の更新とみなしたファイルは、属する更新の期間と一緒に記録する |
| 鍵のファイル | 既定は直下の `.version`。案件ごとに `config/neobit.php` で変えられる（環境ごとではなく案件ごとに決めるもののため）。鍵と分からない、送るたびに書き換えても自然な名前（`VERSION` など）にし、webapp だけが書ける場所に置く。決まりの文書の例の名前は、そのまま使わない。見るのは ctime だけなので中身は何でもよいが、FTP の同期や `rsync` は中身が同じファイルを送らずに飛ばすので、送るたびに日時などを書いて中身を変えるよう、利用ガイドに書く |
| 通常の更新とみなした分 | 通知はしないが、1日1回の報告のメールに、更新の期間ごとにまとめて一覧を載せる（例：「14:00〜14:40 の更新（12件）」）。鍵を悪用されても、翌日には運営者の目に入るようにするため |
| 監視しない場所 | 運用中に正しく変わる `storage/logs`・`storage/framework`・`bootstrap/cache`（基準そのものと `config:cache` の分） |

- 限界：サーバーそのもの（root）を乗っ取られたら、同じサーバーの上の監視は信用できない。外から定期的にページを取得して比べる監視（外部の監視サービス）との組み合わせは、利用ガイドの付録に書く
- 送るたびの手順に、鍵のファイルの更新を足す。サーバーの crontab の設定は、サーバーを管理する人の作業
- 実装の前に、監視するディレクトリの一覧・通知の宛先・メールの文面を決める

- 見張りは、Laravel の入口 `public/index.php` の頭で `require` する。こちらのファイルなので、どのサーバーでも置ける。`auto_prepend_file` と両方で掛かっても、2回目は何もしない

**B. WordPress との共存**（A の見張りを使う）

既存の WordPress のサイトに Laravel を入れるときの置き方と、WordPress の守り。WordPress は `__()` などの関数を条件なしで作り、Laravel と同じ PHP の中では動かせないので、URL で振り分ける。

狙われやすい WordPress を後ろに下げ、自衛の機能が効く Laravel を前に出す。WordPress には決まったコーナーだけを受け持たせ、ほかは Laravel が受ける。「WordPress のサイトの守りも固められる」ことを、このフレームワークの売りの1つにする。

- 分担。入口で止める守り（IP ブロック・メンテナンスの画面・サイトと管理画面のアクセス制限・ベーシック認証）と、ファイルの守り（権限・改ざん監視）はフレームワークが受け持つ。リダイレクトは、`.htaccess` が Laravel より先に WordPress へ回すので、WordPress のコーナーの下には効かない。ログインの守り・操作ログ・スパムの守り・SEO など中の処理は WordPress 次第

- 直下の入口は Laravel。知らない URL も Laravel が受ける（固定ページ・リダイレクト・404 を Laravel で扱う）。WordPress の入口は `wordpress.php` などの名前で置く
- WordPress に回すのは、`.htaccess` の一覧に書いた URL だけ。ディレクトリ単位（`/faq/`・`/shop/`・`/news/` など）と、もしあれば最上位の固定ページ（1件ずつ）、WordPress の動きに要るもの（`wp-admin/`・`wp-includes/`・`wp-content/`・`wp-login.php`・`wp-json/` など）。既存のサイトでは、固定ページはほとんどディレクトリに分かれていて、最上位にはほぼ無い
- 最上位（`/`）に `p`・`page_id`・`post_type`・`preview`・`s` の問い合わせが付いたものも、WordPress に回す。下書きのプレビュー（`/?post_type=news&p=123&preview=true`）・短い URL・検索は、パーマリンクを決めていても最上位で呼ばれるため。Laravel の側では、最上位でこれらの名前を使わない（検索を作るときは `/search?q=` のように別の URL にする）
- 共通のヘッダー・フッターは、Laravel のレイアウトと WordPress のテーマの両方に持つ（どちらを前に出しても変わらない）

**A. 改ざん監視の状況と承認を、管理画面に出す**

- 管理画面の「承認」で、知らせた変化を通常の更新として取り込む。管理画面（apache）は記録を書けないので、承認の目印を `storage` の下に置き、改ざん監視の cron（devapp）が次の回で拾って取り込む（`--accept` と同じ処理）
- 承認できるのは、改ざんの疑いと、判断待ちの変化。自分で更新したと分かっていれば、15分の知らせを待たずに承認できる。画面には2つを分けて並べる。許可されていないアップロードファイルは承認できない。目印には、画面に出した一覧を結び付け、その後に増えた変化はまとめて取り込まない
- `.version` を書き換える正規のメンテナンスのほかで、Web から更新した内容を承認する仕組み。承認したら、記録として「○○さんがサイトの変更内容を承認しました」のメールを、知らせと同じ宛先へ送る。メールには、取り込んだファイルの一覧を必ず載せる。判断待ちを承認したときは、改ざんの知らせが届かないので、このメールが知らせの代わりになる。操作ログと、1日1回の報告（「手で認めた更新」の欄）にも、承認した人の名前を残す
- 二段階認証や合言葉は付けない。apache の権限で侵入した攻撃者は目印を真似できるが、apache はコードに書けないので、真似して取り込ませられるのはアップロードの置き場所の `.htaccess`・`.user.ini` くらい。それも、承認のメール（ファイルの一覧つき）と翌日の報告に残る。誰も承認していないのにメールが届けば、運営者が気付ける。記録さえ残れば足りる
- 画面を開ける人は、スタッフの権限で絞る（管理者など）

- 画面でのファイルの編集は、`DISALLOW_FILE_EDIT` で止めたまま
- 更新で変わったファイルは、更新した人が、A の承認で取り込む。15分を待たずに承認してよい。承認しなければ、15分後に改ざんの疑いとして知らせる。何が変わったかを、毎回人が見て、メールに残ることになる
- 自動更新は、パスワードを聞けないので動かない。セキュリティの更新を自動で当てたい案件は、devapp の crontab から WP-CLI で更新し、最後に `.version` を書き換える形を別に考える

- 更新の専用の SSH の利用者を、案件ごとに作るか（お客さんに devapp のパスワードを渡さないため）
- 管理画面の承認の画面を、フレームワークの画面（ルートを1行で書く形）にするか、案件の画面にするか

- 決めること：A か B か。A なら分け方。`login.php` をフレームワークの側へ移すか

### 段階5　配布の形

2026-10-14 に話した形。案件は数十から100以上を見込む。開発とテストは、今後も memsys で行う。リクエストを受けて memsys で実装とテストをしてから、フレームワークの部分を配り直す。

| リポジトリ | 役割 | 直す人 |
|---|---|---|
| memsys | フレームワークと見本のサイトの両方。`packages/neobit/core/` も git で管理する | 開発する人 |
| 配る用のリポジトリ（新規） | `packages/neobit/core/` の中身だけ。版のタグを付けて配る | 誰も直さない。memsys からの書き出しだけを受け取る |

- 版を出すときに、`git subtree split` で `packages/neobit/core/` の履歴だけを取り出して、配る用のリポジトリへ送る。流れは memsys から配る用への一方向
- 各案件は、`composer.json` に配る用のリポジトリの場所と版を書いて取り込む。案件に `packages/` は無く、フレームワークは `vendor/neobit/core/` に入る
- git submodule にはしない。フレームワークと見本のサイトを、1つのコミットで直せなくなるため
- 配る用のリポジトリは直接直さない。案件で見つかった不具合も、memsys に持ち帰って直す

着手するときに決めること。

- 版の付け方。直しただけの版、機能を足した版、今までの書き方が動かなくなる版を、番号で見分けられるようにする
- 版ごとの変更の記録。案件の側で直すことと、設定の見本が変わったときの案内を書く
- サーバーからの取得。サーバーで `composer install` を実行するので、配る用のリポジトリを読む手段がサーバーごとに要る。読み取り専用の鍵を配るか、認証付きの配布用の置き場を1つ立てるか
- 新しい案件の雛形。memsys からフレームワークを除いた部分も、案件を始めるときの元として配る。雛形の `composer.json` は、手元のパスではなく、配る用のリポジトリの版を見るようにする

### 段階6　文書

- `docs/new-project-files.md` は 2026-10-05 時点の調査。書き換えるファイルの一覧を、切り離した後の形で調べ直す
- 利用ガイドに、設定・画面・メールのテンプレートを上書きする方法と、`vendor:publish` のタグをまとめる
- `docs/project-overview.md` のディレクトリの表を合わせる
- 利用ガイドを、入口と章ごとのファイルに分ける（2026-10-28 に足した。利用ガイドが3千行を超え、章の番号での指し先を直す手間も出てきたため）
  - `docs/neobit-framework-guide.md` は入口にし、章ごとに「何をするものか・いつ使うか・いちばん短い使い方の例・詳しい説明へのリンク」だけを書く。全体を見渡して、どの部品を使えばよいかがすぐ分かるようにする
  - 細かい中身（コントローラーに書くもの・ルート・画面・決まりごと・サーバーの設定など）は、`docs/guide/` の下の章ごとのファイル（例：`docs/guide/27-seo.md`・`29-file-watch.md`）に移す
  - 仕様メモ（`docs/〇〇-spec.md`）は、なぜそう作ったかの記録として残し、章のファイルからリンクする
  - ほかの文書からは、章の番号ではなくファイルの名前で指す。章を足しても指し先が崩れにくくするため
  - 配布の形（段階5）が決まってから始める。どの文書をパッケージと一緒に配るかで、置き場所が変わるため
- 済んだら、この計画書を消すか、設計の記録として残すかを決める

## 段階ごとの進め方

1. 変える予定のファイルを一覧で示し、「go」を待つ
2. 実装する。フレームワークの決まり（`docs/neobit-framework-rules.md`）を先に読む
3. `php artisan test` と `vendor/bin/pint --test` を通す
4. 変更の種類（`add:`・`update:`・`fix:`）ごとにコミットを分ける。`git push` は指示があったときだけ
5. この文書の「状態」を書き換える
