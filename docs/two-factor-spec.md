# memsys 2段階認証の設計

ログインの2段階目を、会員かスタッフかに結び付いた作りから、独立した部品にする。ログインの種類（個人会員・企業会員・スタッフ）ごとに、2段階目の方式をモデルの定数1つで選べるようにする。

版：1.0（2026年10月）

---

## 1. 方針

### 1.1 方式は、モデルごとに1つ選ぶ

2段階目の方式は3つで、列挙型 `TwoFactorMethod` で表す。

| 方式 | 中身 |
|---|---|
| `Email` | メールで送る確認コード（6桁、10分有効） |
| `Totp` | 認証アプリのコード（6桁）。予備にバックアップコード |
| `None` | 2段階目を求めない |

ログインするモデル（`Member`・`CompanyUser`・`Staff`）に、定数 `TWO_FACTOR_METHOD` で書く。方式は、その種類の全員に同じものが効く。本人が方式を選ぶ形にはしない。

定数に既定の値は無い。書いていないモデルでログインするとエラーになる。書き忘れで「なし」になるのを防ぐため。「なし」は、必ず明示して選ぶ。

見本のサイトでは、会員を `Email`、スタッフを `Totp` にしている。

### 1.2 流れは、方式に関係なく1本

1. ID・パスワードを確かめる。まだログインはしない
2. 方式が `None` なら、そのままログインを確定する
3. 信頼済みの端末なら、そのままログインを確定する
4. それ以外は「パスワード確認済み・2段階目が未完了」をセッションに置き、2段階目の画面へ進める
5. 2段階目が通ったら、ログインを確定する

ログインの確定（`Auth::login()`・セッションの作り直し・移動先の決定）は、どの道を通っても同じ1か所で行う。

2の判断は、モデルの定数だけで行う。`Totp` なのにまだ登録していない人を「登録が無いから素通り」にはしない。未登録の人は、4の画面で登録を済ませてからログインする（1.3）。

### 1.3 TOTP の登録と解除

- **登録**：方式が `Totp` で未登録の人は、パスワードを確かめた後の画面で、QR コードを読み取って登録する。登録が済むまでログインできない。登録が済んだら、バックアップコードを1回だけ表示する
- **本人による解除**：ログイン中に、今の認証アプリのコードか、バックアップコードを入力して解除できる。機種を変えるときと、端末を無くしたときに使う。端末を無くした人は、バックアップコードでログインし、別のバックアップコードで解除する。次のログインで登録し直す
- **ログイン中というだけでは、解除させない**：パスワードを知っている人が、信頼済みの端末や開いたままの画面から解除して、自分の認証アプリに付け替えるのを防ぐため
- **運営による解除**：バックアップコードも無くした人は、運営が管理画面から解除する。確認は「する・しない」だけ。スタッフは管理者が、会員は管理画面の会員の詳細から解除する。スタッフは、自分自身を運営として解除することはできない
- **解除は操作ログに残す**：本人による解除も、運営による解除も残す
- **解除で消えるもの**：秘密鍵・バックアップコード・信頼済みの端末・パスキー。パスキーでのログインは2段階目を求めないので、残すと登録し直さないまま使えてしまうため

### 1.4 本人確認も、同じ部品で行う

ログイン中に本人をもう一度確かめる操作（パスキーの登録の前、バックアップコードの作り直し、TOTP の解除）も、その人の方式で確かめる。

| 方式 | 本人確認 |
|---|---|
| `Email` | メールで送る確認コード |
| `Totp` | 認証アプリのコード |
| `None` | パスワードの再入力 |

`None` のときにパスワードを求めるのは、開いたままの画面を使った他人が、パスキーを足して裏口を作るのを防ぐため。

### 1.5 そのほかの決めごと

- パスキーでログインしたときは、方式に関係なく2段階目を求めない（`docs/passkeys-spec.md` の1.1）
- 会員登録・パスワードの再設定・メールアドレスの変更で送る確認コードは、メールアドレスの持ち主かを確かめるもので、ログインの2段階目とは別。方式に関係なく、今までどおりメールで送る
- 方式が `Email` のモデルは、メールアドレスを必須にする。空だとコードを受け取れず、ログインできないため。スタッフのメールアドレスは任意なので、スタッフを `Email` にするときは検証のルールを必須に変える
- 方式が `None` のときは、「この端末を記憶する」のチェックを出さない
- 稼働中のサイトで方式を変えたら、その種類の信頼済みの端末の記録を消す。前の方式で作った記録のため

## 2. 仕組み

### 2.1 ログインする人の共通の型（LoginAccount）

2段階認証の部品は、相手が会員かスタッフかを知らない。ログインするモデルは、共通の型 `App\Support\LoginAccount` を実装し、次の問いに答える。

| メソッド | 答えるもの | 例（スタッフ） |
|---|---|---|
| `loginType()` | 種類の名前。セッションのキー・Cookie・試行制限の名前に使う | `staff` |
| `loginGuard()` | ガードの名前 | `admin` |
| `loginRoute($name)` | ルートの名前 | `admin.login.verify` |
| `loginMailTemplate($name)` | メールのテンプレートの名前 | `staff_verification_code` |
| `twoFactorMethod()` | 2段階目の方式 | `TwoFactorMethod::Totp` |
| `displayName()`・`notificationEmail()`・`loginId()` | 宛名・宛先・ログインに使う値 | |

会員の共通の型 `MemberAccount` は、`LoginAccount` を継ぐ。会員だけの決まり（`memberType()` など）はそのまま残り、`LoginAccount` の問いには、それを使って答える。

### 2.2 テーブル

| テーブル | 列 | 使う方式 |
|---|---|---|
| `t_members`・`t_company_users`・`t_staffs` | `totp_secret`（暗号化して保存）・`totp_confirmed_at` | `Totp` |
| `two_factor_backup_codes` | 会員・スタッフ共通。`authenticatable_type`・`authenticatable_id` で区別 | `Totp` |
| `trusted_devices` | 同上 | `Email`・`Totp` |

TOTP の列は、パスキーのテーブルと同じく、標準の構成として常に持つ。方式の切り替えは、モデルの定数だけで済む。

### 2.3 途中の状態

パスワードを確かめた後、2段階目が終わるまでの状態は、セッションに持つ。キーは種類の名前ごとに分ける（`staff.login.pending_id` など）。同じブラウザで会員と管理画面の両方を使っても、片方のパスワードを通した状態で、もう片方の2段階目を通せないようにするため。

2段階目のルートは、`guest` にも `auth` にも入れない。まだログインしていないので `Auth::check()` では見分けられず、部品がセッションの値で守る。

### 2.4 試行制限

コードの照合の失敗は、種類と人ごとに1本のカウンターで数える（`staff-two-factor` など）。ログインの2段階目・パスキーの登録の前・バックアップコードの作り直し・解除のどこから入力しても、同じカウンターになる。当てようとしている秘密が同じだから。認証アプリのコードとバックアップコードも、同じカウンターで数える。

## 3. フレームワークの部品

| 部品 | 種類 | 役割 |
|---|---|---|
| `App\Enums\TwoFactorMethod` | 列挙型 | 方式の種類 |
| `App\Support\LoginAccount` | インターフェース | ログインする人の共通の型（2.1） |
| `App\Support\HasTwoFactor` | モデルのトレイト | 方式の読み出し、TOTP の列の暗号化、バックアップコードと信頼済みの端末の関連、解除 |
| `App\Support\TwoFactorChallenge` | クラス | その人の方式で「確かめる」。コードの送信と照合、試行制限 |
| `App\Support\TwoFactorLogin` | コントローラーのトレイト | パスワードを確かめた後の流れ（1.2）と、2段階目の画面 |
| `App\Support\TwoFactorManagement` | コントローラーのトレイト | ログイン中の本人による、バックアップコードの作り直しと TOTP の解除 |
| `resources/views/_two_factor.blade.php` | 部分ビュー | 2段階目の画面の中身。方式と状態で、コードの入力か QR コードの登録かを出し分ける |

### 3.1 モデルに書くもの

```php
class Staff extends Authenticatable implements LoginAccount, PasskeyUser
{
    use HasTwoFactor;

    /** ログインの2段階目の方式 */
    public const TWO_FACTOR_METHOD = TwoFactorMethod::Totp;
}
```

### 3.2 ログインのコントローラーに書くもの

```php
use TwoFactorLogin;

/** ログインする人のモデル */
private const LOGIN_ACCOUNT = Staff::class;

/** 2段階目の画面のビュー。中で _two_factor を @include する */
private const TWO_FACTOR_VIEW = 'admin.auth.login-verify';

/** ログインが確定した後の移動先 */
private function loginRedirectUrl(): string
{
    return LoginRedirect::forStaff();
}
```

ID とパスワードを確かめる所は、入力する項目が種類ごとに違うので、コントローラーに書く。合ったら `continueAfterPassword()` を呼ぶ。

| アクション | ルートの名前（`loginRoute()` で頭が付く） |
|---|---|
| `showVerification()`（GET） | `login.verify` |
| `verifyCode()`（POST） | `login.verify.confirm` |
| `resendCode()`（POST。方式が `Email` のときだけ使う。`throttle` を付ける） | `login.verify.resend` |

URL は、どの種類も `…/login/verify` にそろえる。管理画面は `/admin/login/verify`。

### 3.3 本人による管理（TwoFactorManagement）

方式が `Totp` のときに使う。ログイン中の本人が、バックアップコードを作り直し、認証アプリの登録を解除する。作り直しは、今の認証アプリのコードを入力してから行う。解除は、今の認証アプリのコードか、バックアップコードを入力してから行う。

| 種類 | 画面 | コントローラー |
|---|---|---|
| 個人会員 | マイページの「2段階認証」（`/mypage/two-factor`） | `MypageController` |
| 企業会員 | マイページの「2段階認証」（`/company/mypage/two-factor`） | `Company\MypageController` |
| スタッフ | 自分の詳細の画面 | `Admin\StaffController` |

入口は、方式が `Totp` のときだけ出す。画面の中身は、共通の部分ビュー `_two_factor_manage`・`_two_factor_backup_codes` にある。

### 3.4 運営による解除

管理画面の、個人会員・企業の担当者・スタッフの詳細に「2段階認証の登録を解除する」を出す。方式が `Totp` で、登録が済んでいる人にだけ出る。会員と担当者のボタンは、共通の部分ビュー `_two_factor_reset` にある。スタッフは、管理者だけが、自分以外のスタッフを解除できる。

### 3.5 パスキーの登録の前の本人確認

`PasskeyManagement` は、本人確認を `TwoFactorChallenge` に任せる。メールの方式なら確認コードを送って照合し、認証アプリの方式ならコードを照合し、「なし」ならパスワードを照合する。確認コードを送るルート（`passkeys.code`）は、メールの方式のときだけ使う。

認証アプリの方式の人は、認証アプリを登録してある間だけパスキーを持てる。未登録の間は登録に進めず、登録を解除するとパスキーも消える。

### 3.6 テスト

方式はモデルの定数で、実行中には変えられない。テストでは、モデルに用意した差し替えの口（`fakeTwoFactorMethod()`）を、トレイト `Tests\Support\FakesTwoFactorMethod` を通して使う。方式の組み合わせごとの流れは、`tests/Feature/Auth/TwoFactorMethodTest.php` で確かめている。

## 4. 進め方

1. 流れの統一。方式は今のまま（会員は `Email`、スタッフは `Totp`）で、動きは変えない
2. 方式の入れ替えと `None` に対応する。会員の TOTP の列と管理画面からの解除、スタッフ向けの確認コードのメール、ログイン中の本人による管理
3. パスキーの登録の前の本人確認を、`TwoFactorChallenge` に載せ替える。利用ガイドの14章と23章を直す
