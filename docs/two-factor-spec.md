# memsys 2段階認証の設計

ログインの2段階目を、会員かスタッフかに結び付いた作りから、独立した部品にする。ログインの種類（個人会員・企業会員・スタッフ）ごとに、2段階目の方式をモデルの定数1つで選べるようにする。

版：1.1（2026年10月）　1.1：バックアップコードを、使うかどうかをモデルごとに選び、希望する人が自分で発行する形にした（1.4）。解除のコマンドを足した（3.5）

---

## 1. 方針

### 1.1 方式は、モデルごとに1つ選ぶ

2段階目の方式は3つで、列挙型 `TwoFactorMethod` で表す。

| 方式 | 中身 |
|---|---|
| `Email` | メールで送る確認コード（6桁、10分有効） |
| `Totp` | 認証アプリのコード（6桁） |
| `None` | 2段階目を求めない |

ログインするモデル（`Member`・`CompanyUser`・`Staff`）に、定数 `TWO_FACTOR_METHOD` で書く。方式は、その種類の全員に同じものが効く。本人が方式を選ぶ形にはしない。

定数に既定の値は無い。書いていないモデルでログインするとエラーになる。書き忘れで「なし」になるのを防ぐため。「なし」は、必ず明示して選ぶ。

見本のサイトでは、会員を `Email`、スタッフを `Totp` にしている。

### 1.2 流れは、方式に関係なく1本

1. ID・パスワードを確かめる。まだログインはしない
2. 方式が `None` なら、そのままログインを確定する
3. 信頼済みの端末なら、そのままログインを確定する
4. それ以外は「パスワード確認済み・2段階目が未完了」をセッションに置き、2段階目の画面へ進める
5. 2段階目が通ったら、ログインを確定する

ログインの確定（`Auth::login()`・セッションの作り直し・移動先の決定）は、どの道を通っても同じ1か所で行う。

2の判断は、モデルの定数だけで行う。`Totp` なのにまだ登録していない人を「登録が無いから素通り」にはしない。未登録の人は、4の画面で登録を済ませてからログインする（1.3）。

### 1.3 TOTP の登録と解除

- **登録**：方式が `Totp` で未登録の人は、パスワードを確かめた後の画面で、QR コードを読み取って登録する。登録が済むまでログインできない
- **本人による解除**：ログイン中に、今の認証アプリのコードか、バックアップコードを入力して解除できる。機種を変えるときと、端末を無くしたときに使う。端末を無くした人は、発行してあったバックアップコードでログインし、別のバックアップコードで解除する。次のログインで登録し直す
- **ログイン中というだけでは、解除させない**：パスワードを知っている人が、信頼済みの端末や開いたままの画面から解除して、自分の認証アプリに付け替えるのを防ぐため
- **運営による解除**：端末を無くし、バックアップコードも無い人は、運営が管理画面から解除する。確認は「する・しない」だけ。スタッフは管理者が、会員は管理画面の会員の詳細から解除する。スタッフは、自分自身を運営として解除することはできない
- **解除は操作ログに残す**：本人による解除も、運営による解除も残す
- **解除で消えるもの**：秘密鍵・バックアップコード・信頼済みの端末・パスキー。パスキーでのログインは2段階目を求めないので、残すと登録し直さないまま使えてしまうため

- **画面から解除できる人がいないとき**：スタッフが1人だけのサイトなどでは、サーバーでコマンドを実行して解除する（3.5）
- **パスワードの再設定では、解除しない**：解除すると、メールを読める人がパスワードも2段階目も通れてしまうため

### 1.4 バックアップコード

バックアップコードは、2段階目を通れないときに、その代わりに1回ずつ使える緊急用のコード。8桁の数字を10個発行する。認証アプリの入った端末が手元に無いときと、確認コードのメールが届かないときに使う。

- **使うかどうかは、モデルごとに選ぶ**：ログインするモデルに、定数 `BACKUP_CODES`（`true`・`false`）で書く。2段階目を通る手段が1つ増えるので、種類ごとに選べるようにしている。方式が `None` のモデルでは、値に関係なく使わない
- **自動では発行しない**：使うモデルでも、希望する人が、ログイン後の自分の画面で発行する。期限の無いコードを、使うつもりの無い人にまで持たせないため
- **発行の前に、その人の方式で本人を確かめる**：`Totp` は今の認証アプリのコード、`Email` はメールで送る確認コード。再発行すると、前のコードはすべて無効になる
- **発行したコードは、1回だけ表示する**：DB にはハッシュ値で持ち、後からは見せられない
- **入力欄は、発行してある人にだけ出す**：ログインの2段階目と、解除の確認の画面
- **使わないモデルでは、送られてきても通さない**：使う設定の頃に発行したコードが残っていても、通らない

見本のサイトでは、3つのモデルとも `true` にしている。

### 1.5 本人確認も、同じ部品で行う

ログイン中に本人をもう一度確かめる操作（パスキーの登録の前、バックアップコードの発行、TOTP の解除）も、その人の方式で確かめる。

| 方式 | 本人確認 |
|---|---|
| `Email` | メールで送る確認コード |
| `Totp` | 認証アプリのコード |
| `None` | パスワードの再入力 |

`None` のときにパスワードを求めるのは、開いたままの画面を使った他人が、パスキーを足して裏口を作るのを防ぐため。

### 1.6 そのほかの決めごと

- パスキーでログインしたときは、方式に関係なく2段階目を求めない（`docs/passkeys-spec.md` の1.1）
- 会員登録・パスワードの再設定・メールアドレスの変更で送る確認コードは、メールアドレスの持ち主かを確かめるもので、ログインの2段階目とは別。方式に関係なく、今までどおりメールで送る
- 方式が `Email` のモデルは、メールアドレスを必須にする。空だとコードを受け取れず、ログインできないため。スタッフのメールアドレスは任意なので、スタッフを `Email` にするときは検証のルールを必須に変える
- 方式が `None` のときは、「この端末を信頼する」のチェックを出さない
- 稼働中のサイトで方式を変えたら、その種類の信頼済みの端末の記録を消す。前の方式で作った記録のため

## 2. 仕組み

### 2.1 ログインする人の共通の型（LoginAccount）

2段階認証の部品は、相手が会員かスタッフかを知らない。ログインするモデルは、共通の型 `Neobit\Core\Auth\LoginAccount` を実装し、次の問いに答える。

| メソッド | 答えるもの | 例（スタッフ） |
|---|---|---|
| `loginType()` | 種類の名前。セッションのキー・Cookie・試行制限の名前に使う | `staff` |
| `loginGuard()` | ガードの名前 | `admin` |
| `loginRoute($name)` | ルートの名前 | `admin.login.verify` |
| `loginMailTemplate($name)` | メールのテンプレートの名前 | `staff_verification_code` |
| `twoFactorMethod()` | 2段階目の方式 | `TwoFactorMethod::Totp` |
| `displayName()`・`notificationEmail()`・`loginId()` | 宛名・宛先・ログインに使う値 | |

会員もスタッフも、同じ型 `LoginAccount` を実装し、トレイト `IsLoginAccount` を付ける。種類の名前（モデルの短い名前。`member`・`company_user`・`staff`）から、ガード・ルート・メールのテンプレートの名前が決まる。決まりと違う名前にするときだけ、定数 `LOGIN_GUARD`・`LOGIN_ROUTE_PREFIX` を書く。

### 2.2 テーブル

| テーブル | 中身 | 使う方式 |
|---|---|---|
| `two_factor_secrets` | 認証アプリの登録。`secret`（暗号化して保存）・`confirmed_at`。1人につき1行で、登録が済んだ人にだけある | `Totp` |
| `two_factor_backup_codes` | バックアップコード。発行した人にだけある | `Email`・`Totp` |
| `trusted_devices` | 信頼済みの端末 | `Email`・`Totp` |

どれも、会員とスタッフで共通のテーブルで、誰のものかは `authenticatable_type`・`authenticatable_id` で区別する。業務のテーブル（`t_members`・`t_company_users`・`t_staffs`）には、2段階認証のための列を持たせない。方式の切り替えは、モデルの定数だけで済む。

読み書きは、モデルの `HasTwoFactor` を通して行う。`hasTwoFactorConfirmed()`（登録済みか）・`twoFactorConfirmedAt()`（登録日時）・`registerTwoFactor($secret)`（登録）・`resetTwoFactor()`（解除）。

### 2.3 途中の状態

パスワードを確かめた後、2段階目が終わるまでの状態は、セッションに持つ。キーは種類の名前ごとに分ける（`staff.login.pending_id` など）。同じブラウザで会員と管理画面の両方を使っても、片方のパスワードを通した状態で、もう片方の2段階目を通せないようにするため。

2段階目のルートは、`guest` にも `auth` にも入れない。まだログインしていないので `Auth::check()` では見分けられず、部品がセッションの値で守る。

### 2.4 試行制限

コードの照合の失敗は、種類と人ごとに1本のカウンターで数える（`staff-two-factor` など）。ログインの2段階目・パスキーの登録の前・バックアップコードの発行・解除のどこから入力しても、同じカウンターになる。当てようとしている秘密が同じだから。確認コードとバックアップコードも、同じカウンターで数える。

## 3. フレームワークの部品

| 部品 | 種類 | 役割 |
|---|---|---|
| `Neobit\Core\Enums\TwoFactorMethod` | 列挙型 | 方式の種類 |
| `Neobit\Core\Auth\LoginAccount` | インターフェース | ログインする人の共通の型（2.1） |
| `Neobit\Core\Auth\HasTwoFactor` | モデルのトレイト | 方式とバックアップコードを使うかの読み出し、認証アプリの登録・バックアップコード・信頼済みの端末の関連、解除 |
| `Neobit\Core\Auth\TwoFactorChallenge` | クラス | その人の方式で「確かめる」。コードの送信と照合、試行制限 |
| `Neobit\Core\Auth\TwoFactorLogin` | コントローラーのトレイト | パスワードを確かめた後の流れ（1.2）と、2段階目の画面 |
| `Neobit\Core\Auth\TwoFactorManagement` | コントローラーのトレイト | ログイン中の本人による、バックアップコードの発行と TOTP の解除 |
| `app:reset-two-factor` | コマンド | サーバーからの解除（3.5） |
| `packages/neobit/core/resources/views/_two_factor.blade.php` | 部分ビュー | 2段階目の画面の中身。方式と状態で、コードの入力か QR コードの登録かを出し分ける |

### 3.1 モデルに書くもの

```php
class Staff extends Authenticatable implements LoginAccount, PasskeyUser
{
    use HasTwoFactor;

    /** ログインの2段階目の方式 */
    public const TWO_FACTOR_METHOD = TwoFactorMethod::Totp;

    /** バックアップコードを使うか。使うなら、希望する人が自分の画面で発行する */
    public const BACKUP_CODES = true;
}
```

### 3.2 ログインのコントローラーに書くもの

```php
use TwoFactorLogin;

/** ログインする人のモデル */
private const LOGIN_ACCOUNT = Staff::class;

/** 2段階目の画面のビュー。中で _two_factor を @include する */
private const TWO_FACTOR_VIEW = 'admin.auth.login-verify';

/** ログインが確定した後の移動先 */
private function loginRedirectUrl(): string
{
    return LoginRedirect::for(self::LOGIN_ACCOUNT, route('admin.dashboard'));
}
```

ID とパスワードを確かめる所は、入力する項目が種類ごとに違うので、コントローラーに書く。合ったら `continueAfterPassword()` を呼ぶ。

| アクション | ルートの名前（`loginRoute()` で頭が付く） |
|---|---|
| `showVerification()`（GET） | `login.verify` |
| `verifyCode()`（POST） | `login.verify.confirm` |
| `resendCode()`（POST。方式が `Email` のときだけ使う。`throttle` を付ける） | `login.verify.resend` |

URL は、どの種類も `…/login/verify` にそろえる。管理画面は `/admin/login/verify`。

### 3.3 本人による管理（TwoFactorManagement）

ログイン中の本人が、バックアップコードを発行し、認証アプリの登録を解除する。

- **バックアップコードの発行と再発行**：バックアップコードを使うモデルの人ができる。`Totp` は今の認証アプリのコードを入力してから、`Email` はメールで送った確認コードを入力してから行う
- **認証アプリの登録の解除**：方式が `Totp` で、登録が済んでいる人ができる。今の認証アプリのコードか、バックアップコードを入力してから行う

| 種類 | 画面 | コントローラー |
|---|---|---|
| 個人会員 | マイページの「2段階認証」（`/mypage/two-factor`） | `MypageController` |
| 企業会員 | マイページの「2段階認証」（`/company/mypage/two-factor`） | `Company\MypageController` |
| スタッフ | 自分の詳細の画面 | `Admin\StaffController` |

入口は、方式が `Totp` のときと、バックアップコードを使うときに出す。画面の中身は、共通の部分ビュー `_two_factor_manage`・`_two_factor_backup_codes` にある。

### 3.4 運営による解除

管理画面の、個人会員・企業の担当者・スタッフの詳細に「2段階認証の登録を解除する」を出す。方式が `Totp` で、登録が済んでいる人にだけ出る。会員と担当者のボタンは、共通の部分ビュー `_two_factor_reset` にある。スタッフは、管理者だけが、自分以外のスタッフを解除できる。

### 3.5 サーバーからの解除（app:reset-two-factor）

画面から解除できる人がいないときに、サーバーで実行する。スタッフが1人だけのサイトで、その人が端末を無くしたときなど。

```
php artisan app:reset-two-factor staff yamada
```

1つ目は種類の名前（`staff`・`member`・`company_user`）、2つ目はログインに使う値（`loginId()` の値。企業の担当者は `企業ID/ログインID`）。対象の人を出して、確かめてから解除する。`--force` を付けると確かめずに解除する。消えるものは、画面からの解除と同じ。操作ログには、操作した人が空の行として残る。

### 3.6 パスキーの登録の前の本人確認

`PasskeyManagement` は、本人確認を `TwoFactorChallenge` に任せる。メールの方式なら確認コードを送って照合し、認証アプリの方式ならコードを照合し、「なし」ならパスワードを照合する。確認コードを送るルート（`passkeys.code`）は、メールの方式のときだけ使う。

認証アプリの方式の人は、認証アプリを登録してある間だけパスキーを持てる。未登録の間は登録に進めず、登録を解除するとパスキーも消える。

### 3.6 テスト

方式はモデルの定数で、実行中には変えられない。テストでは、モデルに用意した差し替えの口（`fakeTwoFactorMethod()`）を、トレイト `Tests\Support\FakesTwoFactorMethod` を通して使う。方式の組み合わせごとの流れは、`tests/Feature/Auth/TwoFactorMethodTest.php` で確かめている。

## 4. 進め方

1. 流れの統一。方式は今のまま（会員は `Email`、スタッフは `Totp`）で、動きは変えない
2. 方式の入れ替えと `None` に対応する。会員の TOTP の列と管理画面からの解除、スタッフ向けの確認コードのメール、ログイン中の本人による管理
3. パスキーの登録の前の本人確認を、`TwoFactorChallenge` に載せ替える。利用ガイドの14章と23章を直す
