# 個人会員と企業会員を共存させる設計

ネオビットフレームワークを、訪問者側に個人会員と企業会員がいるサイトで使えるようにする。既存のシステムを置き換える案件で、会員のデータを種類ごとのテーブルのまま持ち込めるようにするためである。

版：0.6（2026年10月）　4章の段階は、全部済んだ。使い方は、利用ガイドの23章にまとめてある。残っている課題は5章。
0.6：段階5を2つに分けた。管理画面からの企業の登録は、招待のメールが要るので、段階6へ移した（4章）。
0.5：見本のサイトは、個人会員をメールアドレス、企業会員をログインID にする。個人会員をログインID に切り替える設定は作らない（2.7）。段階の並びを直した（4章）。
0.4：登場する人を、運営・個人会員・企業の担当者の3つに固定した（1.2）。名前は決まりから作り、種類ごとの設定の一覧をやめた（2.1）。企業の担当者の権限をやめ、全員を同じ扱いにした（2.2）。メールアドレスが空の人は、既存のデータの個人情報を1つ照合して登録させる（2.7）。古い方式のハッシュ値は、移すときに今の方式で包む（2.9）。ログアウトと、止めた企業の扱いを足した（2.10）。
0.3：企業会員のログインを、企業ID・担当者ID・パスワードの3つにした。担当者は招待のメールで足す。企業の登録に運営の承認を挟む。

---

## 1. 方針

### 1.1 対象は訪問者側の会員だけ

今は、会員を `Member` の1種類と決めて、共通部品の中で名指ししている。これを、個人会員と企業会員の両方で動く形に直す。

管理側のスタッフは、今までどおり `Staff` の1種類のままにする。

### 1.2 登場する人は、3つに固定する

サイトの形は、「個人会員と運営」か「個人会員と企業会員と運営」のどちらかである。個人会員や企業会員が、さらに何種類にも分かれる案件は、想定しない。登場する人を、次の3つに固定する。

| 人 | モデル | 使うサイト |
|---|---|---|
| 運営 | `Staff` | 全部 |
| 個人会員 | `Member` | 全部 |
| 企業の担当者 | `CompanyUser`（企業は `Company`） | 企業会員のあるサイトだけ |

企業会員の無いサイトは、企業会員のコントローラー・画面・ルートを消す。パスキーを使わないサイトで、該当のルートを消すのと同じ扱いである。

会員の種類を、設定で何種類でも足せる形にはしない。使わない柔軟さのために、設定と共通部品が複雑になるためである。

将来、代理店のような3つ目が要るようになったら、企業会員のモデル・コントローラー・画面・ルートを写して作る。共通部品は、種類の名前をモデルから聞いて動くので（2.1）、触らずに済む。

| 会員 | ログインする人 | ログインに使う値 | 2段階目 |
|---|---|---|---|
| 個人会員 | 本人 | メールアドレスとパスワード。または、ログインID とパスワード | メールの確認コード |
| 企業会員 | その企業の担当者 | 企業ID・担当者ID・パスワード | メールの確認コード（担当者ごとのメールアドレス） |

企業会員は、個人会員と運営会社の中間の立場にある。持っている項目も、できることも、個人会員とは全く違う。

### 1.3 画面もURLも、個人会員と企業会員で分ける

ログイン画面・登録の画面・マイページは、個人会員と企業会員で別のものを用意する。機能が全く違うので、1つの画面を切り替えて使う形にはしない。

1つの画面で両方のログインを受け付ける形も、採らない。同じ値が両方にあったときに、どちらの会員かを決められないためである。

### 1.4 認証は、個人会員と企業の担当者で同じにする

2段階目は、どちらもメールの確認コードにする。会員は毎日使うわけではないので、認証アプリを入れさせる形にはしない。パスキーも、どちらも登録できる。

このため、**メールアドレスは、どちらでも必須**にする。新しく登録するときは、必ず入力させる。既存のデータから移した人でメールアドレスが空の人には、初回のログインで登録させる（2.7）。

### 1.5 企業会員は、担当者の1人ずつを特定する

既存のシステムには、企業に2段階目を求めていないものが多い。全社で1つのログインID とパスワードを使い回している例も多い。担当者の情報を持っていても、参考の程度で、誰がログインしたかの特定には使えない。

2段階目は「その人が本人か」を確かめるものなので、企業にではなく、担当者の1人ずつに付ける必要がある。新しいシステムでは、**個人を特定できる担当者の情報を、きちんと持つ**。企業会員を「企業」と「担当者」に分け、担当者がログインする（2.2）。

既存のシステムのログインID は、**企業ID** として引き継ぐ。その下に、担当者ID を新しく持つ。

### 1.6 既存のデータを、そのまま持ち込めること

- **テーブルは、個人会員と企業会員で分けたままにする**。1つのテーブルにまとめ直すことを求めない。
- **id は振り直さない**。企業の id 1 と個人会員の id 1 が両方あってよい。新しく登録する行の id の始まりは、`app:set-next-id` で決める（利用ガイド16章）。
- **メールアドレスは、重なっていてもよい**。ログインID でログインする場合は、メールアドレスを本人の区別に使わない。企業の代表アドレスを複数の担当者が使っている、家族で1つのアドレスを使っている、といったデータを持ち込めるようにする。
- **メールアドレスは、空でも持ち込める**。初回のログインで登録させる（2.7）。
- **パスワードは、古い方式のハッシュ値から移す**。元のパスワードには戻せないので、移すときに今の方式で包み、本人が次にログインしたときに置き換える（2.9）。

### 1.7 既存のログインID とパスワードは、漏れている前提で扱う

置き換えるのは、脆弱性を抱えた既存のシステムである。そこにあったログインID とパスワードは、もう漏れているかもしれない。

- メールアドレスが空の人の初回のログインでは、ログインID とパスワードのほかに、既存のデータにある個人情報を1つ照合する（2.7）。漏れた ID とパスワードだけでは、他人がアカウントを自分のものにできないようにするためである。
- 古い方式のハッシュ値は、DB にそのまま置かない（2.9）。既に漏れたものは取り戻せないが、新しいシステムから漏れたときの備えになる。

### 1.8 既存のデータがあるサイトだけの機能

次の3つは、既存のシステムからデータを移したサイトだけで働く。新しく始めるサイトでは、対象の会員がいないので、何も起きない。

| 機能 | 働く条件 | 新しく始めるサイトでは |
|---|---|---|
| 初回のログインでの、メールアドレスの登録と個人情報の照合（2.7） | メールアドレスが空の会員がいる | 登録のときにメールアドレスを必ず入れるので、空の会員がいない |
| 移した企業の、初回のログイン（2.8） | 氏名とメールアドレスが空の担当者がいる | 担当者は、登録か招待で作られるので、空の担当者がいない |
| 古い方式のパスワードの置き換え（2.9） | `legacy_password` に値がある会員がいる | 設定の `legacy_passwords` を空にしておく。列は使われない |

新しく始めるサイトは、設定を空のままにし、初回のログインでの登録の画面（`login.setup`・`company.login.setup`）とルートを消してよい。企業会員を使わないサイトで、企業会員の画面を消すのと同じ扱いである。

### 1.9 この設計で扱わないこと

- スタッフの種類を複数にすること
- 1人が、個人会員と企業の担当者の両方を兼ねること。別々のアカウントとして扱う
- 既存のデータを取り込む道具。件数が多いので、CSV 取り込み（利用ガイド10章）とは別に考える（5章の課題）

## 2. 仕組み

### 2.1 会員のモデルの共通の型と、名前の決まり

ログインするモデル（`Member`・`CompanyUser`）は、共通の型 `App\Support\MemberAccount`（インターフェース）を実装する。共通部品は、`Member` と書いていた所を、この型で受け取る。

| メソッド | 返すもの | 使う所 |
|---|---|---|
| `memberType()` | 種類の名前。個人会員は `member`、企業の担当者は `company` | 下の表の名前を作る |
| `displayName()` | 画面やメールに出す名前。個人なら氏名、企業なら「企業名　担当者の氏名」 | お知らせのメールの宛名、操作ログの一覧 |
| `notificationEmail()` | お知らせを送るメールアドレス。未登録なら null | お知らせのメール、確認コード |
| `loginId()` | ログインに使う値。企業の担当者なら「企業ID と担当者ID」 | 試行制限、パスキーの表示名 |

**ルートやテンプレートの名前は、種類の名前から決まりで作る**。設定には書かない。

| もの | 決まり | 個人会員 | 企業の担当者 |
|---|---|---|---|
| ガード | 種類の名前。個人会員だけは `web` | `web` | `company` |
| ルート | 頭に「種類の名前.」。個人会員だけは付けない | `login`・`mypage`・`password.forgot` | `company.login`・`company.mypage`・`company.password.forgot` |
| メールのテンプレート | 頭に「種類の名前_」 | `member_verification_code` ほか | `company_verification_code` ほか |
| 信頼済み端末の Cookie | 「種類の名前_trusted_device」 | `member_trusted_device` | `company_trusted_device` |

個人会員のガードとルートに頭を付けないのは、今の URL とルートの名前を変えないためである。

決まった中身（名前を作る、ログインの列から値を取る）は、トレイト `IsMemberAccount` に用意する。モデルに書くのは、種類の名前と、`displayName()`・`notificationEmail()` になる。共通部品は、渡されたモデルに種類の名前を聞くだけで、個人か企業かの場合分けを持たない。

**設定ファイル（config/members.php）に書くのは、サイトごとに変わるものだけ**にする。

```php
return [
    // 個人会員
    'member' => [
        // 古い方式のパスワードを計算するクラス。書いた順に試す。無ければ空（2.9）
        'legacy_passwords' => [],
    ],

    // 企業の担当者
    'company' => [
        // 初回のログインで担当者の情報を登録するときに、照合する企業の列（2.8）
        'identity_check_column' => 'tel',
        'legacy_passwords' => [
            App\Support\Legacy\Md5Password::class,
            App\Support\Legacy\Sha1Password::class,
        ],
    ],
];
```

ガードそのもの（`config/auth.php`）は、Laravel の設定のまま書く。

### 2.2 企業会員は「企業」と「担当者」に分ける

| テーブル | モデル | 持つもの | ログイン |
|---|---|---|---|
| `t_companies` | `Company` | 企業の情報（企業ID、企業名、住所、電話番号、法人番号など）、状態（2.5）、管理メモ | しない |
| `t_company_users` | `CompanyUser` | 担当者の情報（担当者ID、氏名、パスワード、メールアドレス）。企業に属する | する |
| `t_company_invitations` | `CompanyInvitation` | 担当者の招待（宛先のメールアドレス、期限）。企業に属する（2.4） | ― |

- **ログインするのは担当者**である。2段階目の確認コードは、担当者のメールアドレスに送る。信頼済み端末もパスキーも、担当者ごとに持つ。
- **担当者に、権限の区別は付けない**。同じ権限でログインできる人が、複数いるだけである。どの担当者も、企業の情報の変更、担当者の招待、ほかの担当者の編集と削除ができる。
- **企業の側からの退会の画面は、作らない**。退会は、企業が運営に連絡し、運営の側で対応する。
- **担当者は、自分自身を削除できない**。担当者が1人もいない企業を、企業の側の操作では作らないためである。

操作ログでは、操作した人は担当者（`company_user`）、対象は企業（`company`）や担当者になる。権限の区別が無いぶん、「どの企業の、誰が操作したか」は、操作ログで追う。

### 2.3 企業会員のログイン

ログイン画面では、**企業ID・担当者ID・パスワード**の3つを入力させる。

| 入力 | 中身 | 重ならない範囲 |
|---|---|---|
| 企業ID | 企業を決める値（`t_companies.code`） | 全部の企業を通して |
| 担当者ID | その企業の中で、担当者を決める値（`t_company_users.login_id`） | その企業の中だけ |
| パスワード | 担当者ごと | ― |

企業ID も入力させるので、担当者ID は企業の中だけで重ならなければよい。別の企業に同じ担当者ID があっても構わない。担当者は、覚えやすい ID（名字や社員番号など）を自由に付けられる。

**企業ID の決め方**

| 企業 | 企業ID |
|---|---|
| 新しく登録した企業 | 自動で振る番号。企業の id と同じ値を入れる。始まりの番号は、`app:set-next-id` で決める |
| 既存のデータから移した企業 | 今までのログインID をそのまま使う。`ABC001` のような文字のこともある |

企業ID の列は、文字を入れられる列にし、重ならない制約を付ける。既存のログインID が数字のときは、新しい番号の始まりを、既存の範囲より上にしておく。

**入力の手間を減らす**ために、ログイン画面に「企業ID と担当者ID を記憶する」のチェックを置く。チェックしてログインすると、企業ID と担当者ID を Cookie に覚え、次からは入力済みの状態で画面を出す。パスワードは、ブラウザが覚えたものを入れられるので、押すだけでログインできる。

ログインに関わる「覚える」は、3つになる。役割が違うので、文言で区別する。

| チェック | 置く画面 | 覚えるもの | 効き目 |
|---|---|---|---|
| 企業ID と担当者ID を記憶する | ログイン | 企業ID・担当者ID（Cookie） | 次から、2つの入力が要らない |
| ログイン状態を保持する | ログイン | ログインしていること | ブラウザを閉じても、ログインしたまま |
| このデバイスを記憶する | 2段階目 | この端末を信頼したこと | 次から、2段階目が要らない |

試行制限（`LoginThrottle`）は、企業ID と担当者ID の組で数える。

### 2.4 担当者の追加は、招待のメールで

担当者は、その企業の担当者が、マイページから招待して足す。どの担当者も招待できる。招待する側が担当者ID やパスワードを決めて渡す形にはしない。パスワードを本人のほかに知っている人を、作らないためである。

1. 担当者が、招待する人のメールアドレスを入力する
2. その人に、招待のメールが届く。メールには、登録の画面へのリンクがある
3. 本人がリンクを開き、担当者ID・氏名・パスワードを決める
4. 担当者が作られ、ログインできるようになる

- リンクは、メールアドレスを持っている本人にしか届かない。リンクから登録した時点で、メールアドレスは確かめられたことになる。
- リンクには期限を付ける（7日）。1回使ったら、使えなくなる。
- 招待は、担当者の一覧に「招待中」として出す。送り直しと、取り消しができる。送り直すと、リンクと期限が新しくなり、前のリンクは使えなくなる。期限の切れた招待は、一覧から消える。
- 同じ宛先にもう一度招待すると、前の招待を置き換える。
- リンクから登録が済んだら、確認コードは求めずに、そのままログインさせる。
- リンクに入れる値は、ハッシュ値にして DB に持つ。信頼済み端末の Cookie と同じ扱いである。
- 誰が誰を招待したかは、操作ログに残る。

### 2.5 企業の登録と、運営の承認

企業会員は、運営が承認してから使えるようにする。企業（`t_companies`）に、状態を持たせる。

| 状態 | 意味 | ログイン |
|---|---|---|
| 申請中 | 登録されたが、運営がまだ確かめていない | できない。「承認をお待ちください」と出す |
| 承認済み | 運営が承認した | できる |
| 停止 | 運営が止めた | できない。ログイン中の担当者も、次の操作から使えなくなる（2.10） |

**企業が自分で登録するとき**

1. 企業の情報と、最初の担当者の情報を入力する
2. 最初の担当者のメールアドレスを、確認コードで確かめる
3. 企業と担当者が、「申請中」で作られる。企業ID は、このときに自動で振る。運営に、申請があったことをメールで知らせる
4. 運営が、管理画面で承認する。最初の担当者に、承認されたことと企業ID を、メールで知らせる
5. ログインできるようになる

承認しないときは、理由を添えて却下する。担当者にメールで知らせ、企業と担当者の行は消す。

**運営が、管理画面から登録するとき**（2.6）

1. 運営が、企業の情報と、最初の担当者のメールアドレスを入力する
2. 企業が、「承認済み」で作られる
3. 最初の担当者に、招待のメール（2.4）が届く
4. 本人が、担当者ID・氏名・パスワードを決める

企業の登録の画面を、運営が代わりに入力する形にはしない。その形だと、運営が担当者のパスワードを決めることになるためである。招待の仕組みを使えば、運営は企業の情報だけを入力し、ログインの情報は本人が決められる。

### 2.6 管理画面の企業会員の管理

| 画面 | できること |
|---|---|
| 企業の一覧・検索 | 企業名・企業ID・状態などで探す。CSV のダウンロード |
| 企業の登録 | 運営が企業を登録する。最初の担当者に、招待のメールを送る（2.5） |
| 企業の詳細・編集 | 企業の情報の確認と変更、管理メモ |
| 承認・却下・停止 | 申請中の企業を承認・却下する。承認済みの企業を止める・戻す |
| 担当者の一覧（企業の詳細の中） | その企業の担当者と、招待中の人を出す |
| 担当者の詳細・編集・削除 | 担当者の情報の確認と変更（氏名、メールアドレス、パスワード）、削除 |

- **担当者の追加は、管理画面からは行わない**。担当者を足すのは、その企業の担当者の役目である。
- ただし、**招待のメールを送ること**だけは、管理画面からできるようにする。運営が企業を登録したときの最初の担当者と、担当者が1人もいなくなった企業の立て直しに要る。
- 運営は、最後の1人の担当者も削除できる。退職した人のアカウントを止める、といった対応に要るためである。その後は、招待を送って立て直す。
- 担当者の詳細を開いたことと、変更は、操作ログに残る（会員・スタッフと同じ）。

### 2.7 ログインに使う値と、メールアドレス

**見本のサイトでは、個人会員はメールアドレス、企業会員はログインID でログインする。**

個人会員をログインID に切り替える設定は、作らない。作ると、見本のサイトが使わない形のために、ログイン・パスワードの再設定・会員登録・マイページに「メールアドレスの場合」と「ログインID の場合」の分岐が入り、どちらが動いているのかが読みにくくなるためである。ログインID でのログインは、企業会員で作って確かめる。

個人会員をログインID でログインさせるサイトは、企業会員のログイン・パスワードの再設定・初回のログインでの登録を写して、個人会員のものを作る。企業ID の入力が要らない分、企業会員のものより簡単になる。次の決まりは、そのときも同じである。

- ログインID は、個人会員の中で重ならない。メールアドレスは重なってよい。
- 「メールアドレスでログインする人」と「ログインID でログインする人」が混ざるサイトは、ログインID の列にそろえる。メールアドレスでログインしていた人には、メールアドレスをログインID として入れ、入力欄は「ログインID またはメールアドレス」の1つにする。
- 2つの列のどちらかに一致すれば通す、という形は採らない。ある人のログインID と、別の人のメールアドレスが同じ文字列だったときに、どちらの人かを決められないためである。

**メールアドレス**は、個人会員でも企業の担当者でも必須にする。

- 新しく登録するときは、必ず入力させ、確認コードか招待のリンクで確かめる。
- 既存のデータから移した人で、メールアドレスが空の人は、**初回のログインで登録させる**。メールアドレスでログインする会員は、メールアドレスが空だとログインの入力ができないので、これはログインID でログインする場合だけの話である。見本のサイトでは、企業会員が当たる（2.8）。

  1. ログインに使う値とパスワードを確かめる
  2. メールアドレスが空なら、2段階目の代わりに、登録の画面へ回す
  3. メールアドレスと一緒に、**既存のデータにある個人情報を1つ**入力させる。設定の `identity_check_column` に書いた列（生年月日や電話番号など）と照合する
  4. 合ったら、入力されたメールアドレスに確認コードを送る
  5. コードが合ったら、メールアドレスを保存して、ログインを完了する

  登録が済むまでは、ログインの後の画面には入れない。済めば、次からは普通の2段階目になる。

- 個人情報を照合するのは、既存のログインID とパスワードが漏れている前提で扱うためである（1.7）。ID とパスワードを知っているだけの他人が、自分のメールアドレスを登録して、アカウントを自分のものにすることを防ぐ。
- 照合の失敗は、試行制限（`LoginThrottle`）で数える。総当たりで当てられないようにするためである。
- 照合する列の値も空の人は、本人では登録できない。スタッフに連絡してもらい、スタッフが管理画面からメールアドレスを入れる。
- メールアドレスが空の間は、パスワードの再設定を本人ではできない。スタッフが管理画面からパスワードを変える。

**パスワードの再設定**は、ログインID でログインする場合は、ログインに使う値とメールアドレスの両方を入力させる。企業会員なら、企業ID・担当者ID・メールアドレスの3つである。全部が合う人に、確認コードを送る。メールアドレスが重なっていても、ログインに使う値で1人に決まる。

### 2.8 既存の企業のデータを移す

既存のシステムの企業は、「企業1件に、ログインID とパスワードが1組」であることが多い。担当者の情報は、あっても当てにしない（1.5）。次のように移す。

| 既存のデータ | 移し先 |
|---|---|
| 企業の情報 | `t_companies`。状態は「承認済み」 |
| ログインID | 企業ID（`t_companies.code`） |
| パスワードのハッシュ値 | その企業に1人だけ作る「最初の担当者」の、古い方式のパスワード（2.9） |

最初の担当者は、担当者ID を決まった初期値（たとえば `admin`）、氏名とメールアドレスを空にして作る。初期値は、全部の企業で同じにする。企業への案内に書く値になる。

**移した企業の、初回のログイン**

1. 企業ID（今までのログインID）・担当者ID（初期値）・パスワード（今までのもの）でログインする
2. 氏名とメールアドレスが空なので、2段階目の代わりに、登録の画面へ回す
3. 氏名・メールアドレス・新しい担当者ID・新しいパスワードと、**企業のデータにある情報を1つ**（電話番号など。設定の `identity_check_column`）を入力させる
4. 企業の情報と照合し、合ったら、メールアドレスに確認コードを送る
5. コードが合ったら保存して、ログインを完了する

この人が、その企業の最初の担当者になる。ほかの担当者は、この人がマイページから招待する。

全社で使い回していたパスワードは、初回のログインで変えさせる。知っている人が多く、そのまま1人の担当者のパスワードにするわけにはいかないためである。

置き換えの前に、企業へ案内を出して、窓口になる人に最初にログインしてもらう。

### 2.9 古い方式のパスワード

既存のシステムのパスワードは、MD5 や SHA-1 のような古い方式のハッシュ値で持っていることが多い。元のパスワードには戻せない。古いハッシュ値は短い時間で破られるので、新しいシステムの DB には、そのままでは置かない。

**移すとき**

古いハッシュ値を、今の方式（bcrypt）でもう一度ハッシュ値にして、パスワードの列とは別の列（`legacy_password`）に入れる。パスワードの列は空にしておく。DB に残るのは、今の方式で包んだ値だけになる。

**ログインのとき**

1. パスワードの列が空で、`legacy_password` に値があれば、古い方式で照合する
2. 設定の `legacy_passwords` に書いたクラスを、書いた順に試す。それぞれのクラスで、入力されたパスワードを古い方式のハッシュ値にし、それを `legacy_password` と今の方式で照合する
3. どれかで通ったら、入力されたパスワードを今の方式で保存し、`legacy_password` を消す

古い方式を計算するクラスは、1つの方式につき1つ書く。型は `LegacyPassword` インターフェースで、メソッドは「入力されたパスワードと、その会員を受け取って、古い方式のハッシュ値を返す」の1つである。

- **よくある方式は、フレームワークに用意する**。ソルトの無い MD5・SHA-1・SHA-256 の3つ。設定に並べるだけで使える。
- **そのサイトだけの方式は、サイトごとに書く**。ソルトの付け方や繰り返しの回数は、システムごとに違う。会員を受け取るので、会員ごとのソルトの列も読める。
- **方式が混ざっているデータ**（途中で方式を変えたシステム）は、設定にクラスを並べれば、順に試して通ったものを採る。

この流れは、ログインの照合をする所（Laravel のユーザープロバイダー）に入れる。パスワードを確かめる所の全部に、1か所で効かせるためである。コントローラーには、何も書かない。

`legacy_password` が残っている人は、まだ一度もログインしていない人である。一定の期間が過ぎたら、`legacy_password` を消してパスワードの再設定を求める、という運用ができるよう、残っている件数を数えられるようにしておく。

包んでおくことは、既に漏れているパスワードには効かない。新しいシステムの DB が漏れたときに、古いハッシュ値から短い時間でパスワードを割り出されることを防ぐ、という備えである。

### 2.10 テーブル・ガード・ログアウト

**フレームワーク内部のテーブルは、変えない**。信頼済み端末（`trusted_devices`）・パスキー（`passkeys`）・操作ログ（`t_operation_logs`）は、相手を「種類と id」の組で持っている。企業の担当者の id 1 と個人会員の id 1 があっても、種類が違うので混ざらない。

企業会員を入れるときに書くのは、次のとおり。

- `config/auth.php` のガードとプロバイダー（`company`）
- `AppServiceProvider` の `enforceMorphMap()`。`company`（企業）と `company_user`（担当者）の2つ
- 操作ログの種類（`OperationLogSubject`）。企業と担当者を足し、担当者を「操作した人」に加える

**ガードは、個人会員・企業の担当者・スタッフで1つずつ**持つ。同じブラウザで、3つに同時にログインできる。運営のスタッフが、企業の側の画面を確かめながら管理画面で操作する、といった使い方を想定する。

- **ログアウトは、その種類の分だけにする**。今は、ログアウトのときにセッションを丸ごと捨てるので、同じブラウザのほかの種類のログインも切れる。そのガードのログインだけを消す形に直す。
- **戻り先を、種類ごとに覚える**。ログインが必要な画面を開こうとしてログイン画面へ回されたとき、ログインの後で元の画面へ戻す仕組み（`LoginRedirect`）は、今は会員と管理画面の2つを、ルートの名前の頭（`admin.`）で見分けている。3つになると見分けられないので、種類ごとに覚える形に直す。
- **止めた企業の担当者は、次の操作から使えなくする**。企業の状態は、ログインのときだけでなく、企業会員の画面を開くたびに確かめる（ミドルウェア）。承認済みでなければ、ログアウトさせてログイン画面へ回す。

| 部品 | 役割 |

## 5. 決めたこと・残っている課題

### 決めたこと

| 項目 | 決めたこと |
|---|---|
| 登場する人 | 運営・個人会員・企業の担当者の3つに固定する。種類を設定で足せる形にはしない（1.2） |
| 画面とURL | ログイン・登録・マイページは、個人会員と企業会員で分ける。企業会員は `/company` の下（2.11） |
| 認証 | 個人会員も企業の担当者も同じ。メールの確認コードと、パスキー。認証アプリは求めない |
| メールアドレス | どちらも必須。空の人は、初回のログインで、既存のデータの個人情報を1つ照合して登録させる（2.7） |
| 企業会員の形 | 企業と担当者に分ける。担当者の1人ずつを特定する。担当者に権限の区別は付けない（2.2） |
| 企業会員のログイン | 企業ID・担当者ID・パスワードの3つ。担当者ID は、企業の中だけで重ならなければよい。企業ID と担当者ID は、ブラウザに記憶させられる（2.3） |
| 企業ID | 新しい企業は、番号を自動で振る。既存のログインID は、企業ID として引き継ぐ（2.3） |
| 担当者の追加 | 招待のメールで足す。どの担当者も招待できる（2.4） |
| 企業の登録 | 運営が承認してから、ログインできる（2.5） |
| 企業の退会 | 企業の側の画面は作らない。企業が運営に連絡し、運営の側で対応する（2.2） |
| 管理画面 | 企業の登録と、担当者の確認・編集・削除ができる。担当者の追加はしない。招待のメールだけは送れる（2.6） |
| 古い方式のパスワード | 移すときに、今の方式で包む。計算のクラスを設定に並べ、順に試す（2.9） |
| 個人会員のログイン | 見本のサイトではメールアドレス。ログインID に切り替える設定は作らず、要るサイトは企業会員のものを写す（2.7） |
| 自動テスト | 認証の流れから作る。載せ替えの前に作り、段階ごとに足す（4章） |
| 見本のサイト | 個人会員と企業会員の両方を入れる |

### 案として書いたもの（違えば直す）

- 移した企業の、最初の担当者の担当者ID は、全部の企業で同じ初期値にする（2.8）
- 却下した企業は、行を消す（2.5）
- 担当者は、自分自身を削除できない（2.2）
- 照合する情報は、企業の電話番号を見本にする（2.1）。サイトごとに設定で変えられる

### 残っている課題

- **既存のデータを取り込む道具**。数万件から数十万件を、元の id ごと取り込む。今の CSV 取り込みは、画面から1件ずつ検証して保存する作りで、この件数には向かない。コマンドから取り込む形を、別に設計する。古いハッシュ値を今の方式で包む処理（2.9）は、1件ごとに時間がかかる。10万件で数時間になるので、取り込みとは別に、裏で少しずつ進める形が要る。
- **ログインに使う値の、同じ・違うの基準**。既存のシステムでは別々の ID だったものが、新しい DB では同じと見なされることがある（大文字と小文字、全角と半角、前後の空白）。取り込みの道具を設計するときに、既存のシステムの基準を調べて、列の設定を合わせる。
- **ログインに使う値が、重なっているデータ**。取り込む前に直すか、取り込むときに印を付けて、スタッフが直すまでログインさせない。
- **サイトを開けた直後の、確認コードのメールの集中**。開けた直後は、全員が初回のログインで、確認コードのメールが要る。レンタルサーバーの送信の上限（15分に100通ほど）では足りない。本番では、上限の大きいメールのサービスを使うか、案内を会員ごとにずらす。
- **担当者が1人もいなくなった企業**。運営が招待を送って立て直す（2.6）。企業の側から運営に頼む窓口を、どこに置くかは決めていない。
