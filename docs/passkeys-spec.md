# memsys パスキーの設計

ネオビットフレームワークに、パスキー（WebAuthn）でのログインを加える。会員（訪問者側）と管理画面（スタッフ）の両方で使え、サイトごとに入れるかどうかを、ルートとコントローラーの `use` で切り替えられるようにする。

版：1.1（2026年10月）　1.1：パスワードを変えたらパスキーも消し、お知らせのメールを送るようにした（2.6）

---

## 1. 方針

### 1.1 パスキーだけでログインできる（A案）

ログイン画面に「パスキーでログイン」のボタンを置き、パスキーで通ったときは、ログインID・パスワードも、2段階目（会員：メールの確認コード、管理：認証アプリのTOTP）も求めずにログインさせる。

パスキーは、端末を持っていること（所持）と、指紋・顔・PINで端末のロックを解いたこと（生体・知識）を1回で確かめる。そのため、パスキーだけで「2要素で確かめた」ことになる。

TOTPの代わりに2段階目としてだけ使う方法（B案）は採らない。B案では、認証アプリを開いてコードを手で入力する手間が減るだけで、パスワードの入力は残るからである。

ログインID・パスワードでのログインは、今までどおり残す。パスキーを登録していない人や、パスキーの入った端末を失くした人のためである。

### 1.2 登録の前に本人確認をする

パスキーを登録すると、以後はそのパスキーだけでログインできるようになる。ログイン中の画面を他人に使われたときに、その人のパスキーを足されないよう、登録の前に本人確認をする。

確かめ方は、**その人のログインの2段階目と同じ方法**にする。

| 対象 | 本人確認 |
|---|---|
| 会員 | メールで送る確認コード（6桁、10分有効） |
| スタッフ | 認証アプリのTOTPコード（6桁） |

本人確認が済んでから10分の間だけ登録できる。1件登録したら本人確認は使い切りになるので、もう1件登録するときは、もう一度確かめる。

削除には本人確認を求めない。ログインの手段が減るだけで、他人が入れるようになるわけではないからである。

### 1.3 そのほかの決めごと

- ログインした後に「パスキーを登録しませんか」という案内は出さない。登録は、マイページ（会員）と「自分の情報」（スタッフ）の入口から、本人が選んだときだけ行う
- パスキーは1人で複数登録できる。PCとスマートフォンのように、端末ごとに登録する使い方を想定している
- パスキーの名前は入力させず、自動で付ける（2.3）
- 一覧には、登録日・最後に使った日時・最後に使った端末を出す。使っていないパスキーを見分けて消せるようにするため
- 会員の「ログイン状態を保持する」は、パスキーでのログインにも効く。管理画面のログイン画面にある同じチェックボックスも同様
- 管理画面の「2段階認証の登録解除」では、そのスタッフのパスキーも削除する（2.6）

## 2. 仕組み

### 2.1 使うパッケージ

| 種類 | パッケージ | 役割 |
|---|---|---|
| サーバー（composer） | `laravel/passkeys`（v0.2系） | 登録・照合の処理（内部で `web-auth/webauthn-lib` を使う） |
| ブラウザ（npm） | `@laravel/passkeys`（v0.4系） | 端末とのやりとり（内部で `@simplewebauthn/browser` を使う） |

どちらもLaravel公式だが、まだv0系である。版が上がると使い方が変わることがあるので、更新するときは変更点を確かめる。

`laravel/passkeys` は、パスキーのテーブル・ルート・コントローラー・ガードを一式用意しているが、どれも「1種類のユーザー・1つのガード」を前提にしている（テーブルは `user_id` 列、ガードは設定で1つだけ）。memsysは会員とスタッフの2種類があるため、パッケージからは**登録・照合の処理（Actionクラス）だけを使い**、テーブル・ルート・コントローラーは自前で用意する。

| パッケージの部品 | memsysでの扱い |
|---|---|
| Actionクラス（`GenerateRegistrationOptions`・`StorePasskey`・`GenerateVerificationOptions`・`VerifyPasskey`・`DeletePasskey`） | そのまま使う |
| `Passkey` モデル | 継承した `App\Models\Passkey` に差し替える（`Passkeys::usePasskeyModel()`） |
| `PasskeyUser` インターフェース | `Member`・`Staff` に実装する（`App\Support\HasPasskeys`） |
| マイグレーション | 使わない（自前のマイグレーションで作る） |
| ルート・コントローラー | 使わない（`Passkeys::ignoreRoutes()`） |

### 2.2 テーブル

`trusted_devices`・`two_factor_backup_codes` と同じく、認証の仕組みを支えるデータなので、`t_` を付けない汎用のテーブル `passkeys` を会員・スタッフ共通で使う。誰のパスキーかは `authenticatable_type`（`member`・`staff`）と `authenticatable_id` の2列で表す。

| 列 | 内容 |
|---|---|
| `authenticatable_type` / `authenticatable_id` | 持ち主 |
| `name` | 一覧に出す名前（2.3） |
| `credential_id` | パスキーのID（一意）。ログイン時はこの列で探す |
| `credential` | 公開鍵・署名カウンターなど、照合に使う情報（JSON） |
| `last_used_at` / `last_used_device` | 最後にログインに使った日時と端末 |

外部キー制約は付けられないので、退会・2段階認証の登録解除では、呼び出し側で明示的に消す。

### 2.3 パスキーの名前

登録したときに、次の2つから自動で作る。

- 認証器の名前：登録の結果に含まれるAAGUID（認証器の種類を表すID）から、パッケージの対応表で引く（例：Google Password Manager、Windows Hello、iCloud Keychain）
- 端末：User-AgentからOSとブラウザの名前を取る（例：Windows・Chrome）。バージョンは付けない。更新のたびに変わり、同じ端末なのに別の名前に見えてしまうからである

例：「Google Password Manager（Windows・Chrome）」。AAGUIDから名前を引けない認証器（AAGUIDを送ってこないものなど）は「iPhone・Safari」のように端末だけになる。

最後に使った端末（`last_used_device`）も同じ作り方で、ログインのたびに書き換える。

### 2.4 ログインの流れ

1. ログイン画面の「パスキーでログイン」を押す
2. ブラウザがサーバーから「オプション」（毎回違うランダムな値＝チャレンジを含む）を受け取る。サーバーは同じものをセッションに控える
3. 端末が、このサイトのパスキーの一覧を出す。利用者が選び、指紋・顔・PINでロックを解くと、端末がチャレンジに署名する
4. サーバーは、セッションに控えたオプションと署名を突き合わせ、パスキーの公開鍵で署名を確かめる
5. 通ったらログインさせ、移動先（会員：元の画面かマイページ、管理：管理画面TOP）へ移る

控えたオプションは1回使ったら消すので、同じ署名を2回送られても、2回目は通らない。

失敗したときの試行制限は、ルートの `throttle` で掛ける。パスキーは署名を当て推量で作ることができないので、パスワードのようなアカウント単位の制限（LoginThrottle）は使わない。

### 2.5 会員とスタッフのパスキーの区別

会員とスタッフのパスキーは、同じサイト（同じドメイン）のものとして端末に保存される。そのため、ブラウザのパスキー選択画面には両方が並ぶ。見分けが付くよう、スタッフのパスキーは「管理画面：ログインID」という名前で端末に保存する。

管理画面のログインで会員のパスキーを選ぶ（またはその逆の）ことができてしまうので、照合の前に、パスキーの持ち主がそのログイン画面のガードのモデル（会員側は `Member`、管理側は `Staff`）かどうかを確かめ、違えば断る。論理削除したスタッフのパスキーも、持ち主が見つからない扱いになり、ログインできない。

### 2.6 ほかの操作との関係

| 操作 | パスキー |
|---|---|
| 退会（会員） | 削除する |
| 2段階認証の登録解除（管理者による代理・本人の両方） | 削除する |
| スタッフの削除（論理削除） | 残す。削除中はパスキーでもログインできず、削除を取り消すと元どおり使える（パスワード・2段階認証の設定と同じ扱い） |
| パスワードの変更・再設定（会員・スタッフ、本人・管理画面のどちらからでも） | 削除する |

パスワードを変えたときは、パスワードと別に持っているログインの手段（信頼済み端末とパスキー）をすべて無効にし、登録されているメールアドレスへ「パスワードが変更されました」のお知らせを送る（`App\Support\PasswordChange`。スタッフはメールアドレスが空なら送らない）。乗っ取りを疑ってパスワードを変えた場合に、他人が足したパスキーが残らないようにするためで、変えた理由を問わず「パスワードを変えたら、ほかのログインの手段はすべてリセットされる」と説明できる形にしている。スタッフの2段階認証（認証アプリ）は消さない。秘密鍵は本人のスマートフォンの中にあり、パスワードとは別の要素だからである。お知らせのメールは、本人以外が変えた場合に本人が気付けるようにするもので、管理画面から変えたときはその旨（スタッフへは変えた管理者の名前）を添える。

2段階認証の登録解除でパスキーも消すのは、パスキーでのログインは2段階目（TOTP）を求めないためである。パスキーを残すと、TOTPを登録し直さないまま使い続けられ、パスキーを追加するときの本人確認（TOTP）ができない状態になる。「スタッフのパスキーは、TOTPを登録済みの間だけ存在する」という形に揃えている。

### 2.7 動かせる環境

パスキーは、HTTPSのページ（開発時の `localhost` は例外）でしか使えない。パスキーはドメインに結び付けて保存され、サーバーは `APP_URL` からドメイン（RP ID）と許可するオリジンを決める。そのため、`.env` の `APP_URL` を、ブラウザで開いているアドレスと完全に同じ（`https://`・ホスト名・ポート）にしておく必要がある。

あるドメインで登録したパスキーは、別のドメインでは使えない。開発環境（`dev.example.jp`）で登録したパスキーは本番（`demo.example.jp`）では使えないので、それぞれで登録する。

## 3. フレームワークの部品

### 3.1 一覧

| ファイル | 役割 |
|---|---|
| `app/Support/PasskeyLogin.php` | パスキーでのログイン（ログインのコントローラーに `use`） |
| `app/Support/PasskeyManagement.php` | 本人によるパスキーの一覧・登録・削除（コントローラーに `use`） |
| `app/Support/PasskeyCeremony.php` | オプションのセッションへの控え・取り出しと、ブラウザから届いた結果の読み取り（上の2つが共通で使う） |
| `app/Support/HasPasskeys.php` | `Member`・`Staff` に付けるトレイト（`PasskeyUser` の実装） |
| `app/Support/UserAgentLabel.php` | User-Agentから「Windows・Chrome」のような名前を作る |
| `app/Models/Passkey.php` | パッケージの `Passkey` モデルを継承し、持ち主を2列で表す |
| `resources/views/_passkeys.blade.php` | 一覧・本人確認・登録の画面の中身（会員・管理共通） |
| `resources/js/passkeys.js` | ボタンと `@laravel/passkeys` のつなぎ込み、エラーの文言、削除の確認 |
| `app/Support/PasswordChange.php` | パスワードを変えたときの後始末（信頼済み端末・パスキーの無効化と、お知らせのメール `member_password_changed`・`staff_password_changed`） |

`Member`・`Staff` の `HasPasskeys`、`passkeys` テーブル、パッケージは、フレームワークの標準構成として常に入れておく。パスキーを使うかどうかは、次の3.2・3.3のとおり、ルートとコントローラーの `use` で切り替える。

### 3.2 ログイン（PasskeyLogin）

ログインのコントローラーに `use PasskeyLogin;` を書き、定数とメソッドを1つずつ用意する。

```php
use PasskeyLogin;

private const PASSKEY_GUARD = 'web';           // ログインさせるガード

private function passkeyRedirectUrl(): string // ログイン後に移動するURL
{
    return redirect()->intended(route('mypage'))->getTargetUrl();
}
```

トレイトが用意するアクションは `passkeyLoginOptions()`（GET、オプションを返す）と `passkeyLogin()`（POST、照合してログイン）の2つで、どちらもJSONを返す。ルート名は `login.passkey.options`・`login.passkey`（管理画面は `admin.` を付ける）にする。ログイン画面は `Route::has('login.passkey')` のときだけボタンを出すので、ルートを消せばボタンも消える。

### 3.3 一覧・登録・削除（PasskeyManagement）

コントローラーに `use PasskeyManagement;` を書き、定数を4つ用意する。

```php
use PasskeyManagement;

private const PASSKEY_GUARD = 'web';                          // ログイン中の本人を取るガード
private const PASSKEY_ROUTE = 'mypage.passkeys';              // 一覧画面のルート名
private const PASSKEY_VIEW = 'mypage.passkeys';               // 一覧画面のビュー
private const PASSKEY_THROTTLE_SCOPE = 'member-passkey-code'; // 本人確認のコードの試行制限
```

スタッフの `PASSKEY_THROTTLE_SCOPE` は `TwoFactorChallengeController::THROTTLE_SCOPE` にする。ログインの2段階目・バックアップコードの再発行・2段階認証の登録解除と同じカウンターで、TOTPコードの失敗回数を数えるためである。

| アクション | メソッド | ルート名 | 内容 |
|---|---|---|---|
| `passkeyIndex()` | GET | `PASSKEY_ROUTE` | 一覧画面 |
| `passkeySendCode()` | POST | `.code` | 本人確認の確認コードをメールで送る（会員だけ。スタッフはルートを作らない） |
| `passkeyConfirm()` | POST | `.confirm` | 本人確認のコードを照合する |
| `passkeyRegistrationOptions()` | GET | `.options` | 登録用のオプション（JSON） |
| `passkeyStore()` | POST | `.store` | 登録（JSON） |
| `passkeyDestroy()` | DELETE | `.destroy` | 削除（ルートの `{passkey}` はパッケージが `App\Models\Passkey` として読み込む） |

本人確認の方法は、トレイトが持ち主の種類（`Member`・`Staff`）で決める。画面ごとの設定ではなく「その人のログインの2段階目と同じ」という決まりなので、定数にはしていない。

一覧画面のビューは、`_passkeys.blade.php` を `@include` するだけの薄い画面にする。入口（マイページ・スタッフ詳細のリンク）は `Route::has()` のときだけ出す。

### 3.4 memsysでの組み込み先

| 画面 | コントローラー | ルート名 |
|---|---|---|
| 会員のログイン | `AuthSessionController`（PasskeyLogin） | `login.passkey.options`・`login.passkey` |
| 会員のパスキー（マイページ） | `MypageController`（PasskeyManagement） | `mypage.passkeys` ほか |
| 管理画面のログイン | `Admin\AuthSessionController`（PasskeyLogin） | `admin.login.passkey.options`・`admin.login.passkey` |
| スタッフのパスキー（自分の情報） | `Admin\StaffController`（PasskeyManagement） | `admin.passkeys` ほか |

スタッフのパスキーの画面は、本人だけのもの（URLに `{staff}` を含まない）。他のスタッフの詳細画面には、登録件数だけを出す。

## 4. 残っている課題

- スタッフが自分のパスワードを変えるときの本人確認（TOTPの再確認）は、パスキーとは別の話として後で検討する
- 端末に残ったパスキーは、サイトから消せない。サイトで削除した後は、端末の設定から消してもらう（削除の完了メッセージで案内している）
- パッケージがv0系のため、版を上げるときは、Actionクラスの引数と `PasskeyUser` インターフェースに変更が無いかを確かめる
