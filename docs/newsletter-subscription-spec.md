# 仕様メモ：メルマガだけの申し込み（newsletter-subscription）

- 実装プロンプト：`docs/prompt/newsletter-subscription.md`
- 実装完了日：2026-10-20

## A. 概要

**目的・解決する課題**

会員登録をしなくても、お知らせメール（一斉メール）だけを受け取りたい人を受け付ける。あわせて、これまで操作ログに残すだけで一斉メールでは止められなかった「会員ではない人の配信停止」と、会員の情報が消えると失われていた「退会した人の配信停止」を記録し、一斉メールで送らないようにする。

**対象範囲**

| 含む | 含まない |
|---|---|
| 訪問者向けの申し込み（`/newsletter`）。確認コードでの本人確認 | 一斉メールの宛先を「メルマガ希望者全員」として直接選ぶ仕組み（CSV を落として読み込む運用） |
| 会員ではない人の「受け取る／受け取らない」のテーブル | 企業会員の担当者のお知らせメール |
| 配信停止の URL・会員登録・退会とのつながり | 戻ってきたエラーのメール（バウンス）からの自動の停止 |
| 一斉メールの宛先の CSV での停止の確認と、メルマガ希望者の CSV のダウンロード | メルマガだけの人が自分で停止を取り消す画面（もう一度申し込めば戻る） |
| 管理画面のメルマガ希望者の一覧・検索・停止 | 管理画面からの手での登録 |
| 確認コードの部品に、使い道の名前を渡す引数（`purposeLabel`）を足す | |

## B. 実装仕様

**データ構造**：`t_newsletter_subscribers`（モデル `App\Models\NewsletterSubscriber`）

| 列 | 型 | 中身 |
|---|---|---|
| `id` | bigint | |
| `name` | varchar(100) null | 氏名（ニックネームでも可）。停止だけで作った行は空 |
| `email` | varchar(255) unique | メールアドレス |
| `notice_mail` | tinyint | 受け取る（1）／受け取らない（0）。会員と同じ列挙型 `App\Enums\NoticeMail` |
| `source` | varchar(30) | 最後に受け取るかを決めた経路。`form`・`unsubscribe_link`・`withdrawal`・`admin`（`App\Enums\NewsletterSource`） |
| `subscribed_at` | datetime null | 確認コードが通って「受け取る」にした日時（同意の記録） |
| `unsubscribed_at` | datetime null | 「受け取らない」にした日時 |
| `ip` | varchar(45) null | 申し込み・停止のときの IP アドレス（同意の記録） |
| `created_at`・`updated_at` | | |

**業務ルール**

- 同じアドレスの「受け取るか」は、どの時点でも1か所だけで持つ。会員は `t_members.notice_mail`、会員ではない人は `t_newsletter_subscribers`。
- 申し込み：確認コードが通った後、会員のアドレスなら会員の `notice_mail` を「受け取る」にする（行は作らない）。会員でなければ行を「受け取る」にする（無ければ作る、あれば戻す）。完了の画面はどちらも同じ文。
- 停止（配信停止の URL・管理画面・退会）：会員ではないアドレスの行を「受け取らない」にする。行が無ければ「受け取らない」の行を作る。すでに「受け取らない」の行は変えない（最初に止めた日時と経路を残す）。
- 会員登録：同じアドレスの行を消す。受け取るかは、登録の画面で本人が選んだもの。
- 退会（マイページ）：「受け取る」だった会員は「受け取らない」の行を残す（経路は退会）。
- 一斉メール：宛先の CSV に、会員の側か行の側で「受け取らない」のアドレスがあると、その行をエラーにする。エラーの文は「お知らせメールの配信を停止しているアドレスです。宛先から外してください。」（会員とそれ以外で同じ文）。
- メルマガ希望者の CSV：「受け取る」の会員と、「受け取る」の行の人。会員が先で、同じアドレスは1行。「氏名, メールアドレス」の2列、見出しなし、UTF-8（BOM 付き）。ダウンロードの記録と操作ログを残す。

**入力・検証**（申し込み）

- 氏名：必須、100文字まで、改行なし（一斉メールの件名に差し込むことがあるため）
- メールアドレス：必須、`email:rfc`、255文字まで
- スパム対策：`SpamGuard`（ハニーポット・表示から送信までの時間・Turnstile）。機械と判定したら、完了の画面へ回して何もしない
- 回数の制限：送信 5回／分（IP）、再送 3回／分（IP）、確認コードの送信 5回／時（アドレス）、コードの照合の失敗（`LoginThrottle`、IP とアドレス）

**外部連携**

- 確認コードのメール：`LoginVerificationCode::issueForAddress()` に、使い道 `'newsletter'` と `purposeLabel: 'メルマガの登録'` を渡す。テンプレートは会員の `member_verification_code`。件名は「【サイト名】メルマガの登録のお手続き」。
- Cloudflare Turnstile（`SpamGuard`）。

**処理フロー**

1. `/newsletter` で氏名とメールアドレスを入れる → スパム対策 → 検証 → セッションに仮置き → 確認コードを送る
2. `/newsletter/verify` でコードを入れる → 照合 → `NewsletterSubscription::subscribe()` → `/newsletter/done`
3. 一斉メールの入力の画面で「メルマガ希望者のCSVをダウンロード」 → 宛先として読み込む → 停止しているアドレスは確認画面でエラー

**操作ログ**

| 操作 | 対象 |
|---|---|
| メルマガの登録（`newsletter_subscribe`） | 会員のアドレスなら会員、そうでなければメルマガの行 |
| メルマガの停止（`newsletter_stop`） | 管理画面で止めた行 |
| お知らせメールの配信停止（既存） | 会員ではない宛先のときは、補足の結果を「会員ではない宛先」にした |

## C. 前提・依存

- 会員の `notice_mail` 列と `App\Enums\NoticeMail`（既存）
- 配信停止の URL（`App\Services\MailUnsubscribe`）、一斉メール（`Admin\BulkMailController`）、CSV の書き出し（`Neobit\Core\Csv\CsvWriter`）
- 確認コード（`Neobit\Core\Auth\LoginVerificationCode`）。今回、`issueForAddress()` に省略可の引数 `purposeLabel` を足した
- スパム対策（`Neobit\Core\Security\SpamGuard`）と Turnstile の鍵（`.env`）
- 管理画面のルートは、一斉メールと同じ管理者だけのグループ（`EnsureStaffIsManager`）

## D. 設計判断とトレードオフ

| 判断 | 採用 | 不採用とその理由 |
|---|---|---|
| 受け取るかの持ち方 | 会員は会員のテーブル、会員ではない人だけを新しいテーブル。連動は会員登録と退会の2つだけ | 全員を新しいテーブルで持ち毎回連動させる：書き換える場所が多く、漏れるとずれる。会員の列をやめて新しいテーブルだけにする：会員の画面・CSV・一斉メールを広く作り直すことになる |
| 本人確認 | 会員登録と同じ確認コードを流用 | 確認のリンクを送る形：新しい仕組みが要る。部品をそのまま使えるコードのほうが、作る量が少なく、画面の流れも会員登録と揃う |
| 確認コードの件名 | 部品に `purposeLabel` を足す | 部品に `PURPOSE_NEWSLETTER` を足す：メルマガは案件の機能で、フレームワークが名前を知る理由がない。確認コードを案件の側で別に作る：写した処理が食い違いのもとになる |
| 会員のアドレスでの申し込み | 会員の側を「受け取る」にし、完了の文は同じ | 「会員の方はマイページで」と出す：そのアドレスの会員がいるかが外から分かってしまう |
| 会員登録のときの受け取るか | 登録の画面で本人が選んだものにし、行は消す | 行の値を引き継ぐ（プロンプトの記載）：登録の画面で「受け取る」を選んだのに、前に止めた行の値で「受け取らない」になると、本人の今の意思に反する。いちばん新しい本人の意思を採った ※実装時にプロンプトから変えた点 |
| 宛先の選び方 | メルマガ希望者の CSV を落として読み込む | 宛先に「全員」を選べるようにする：一斉メールの流れ（CSV の確認・エラーの行）を作り直すことになる |
| 停止の文言 | 会員とそれ以外で同じ文 | 会員だけ別の文：管理画面の中なので漏れの心配は無いが、運用で区別する必要が無い |
| 管理画面のメニューの位置 | 「運用」の見出し（管理者だけ）の、一斉メールの次 | 「会員」の見出し（プロンプトの記載）：ルートが管理者だけなので、管理者でない人にも見えるメニューに置くと、押すと自分の情報の画面へ回されてしまう ※実装時にプロンプトから変えた点 |

## E. 課題・懸念点

| 重要度 | 内容 |
|---|---|
| 中 | メルマガだけの人が停止を取り消す画面は無い。もう一度申し込めば「受け取る」に戻る |
| 中 | 会員がメールアドレスを変えたとき、古いアドレスの「受け取らない」の記録は残らない。会員の側で持っているため（退会のときだけ行を残す） |
| 中 | バウンス（届かなかったメール）からの自動の停止は無い。戻り先（`MAIL_RETURN_PATH`）のメールボックスを人が見る運用 |
| 低 | 停止だけで作った行（配信停止の URL・退会）は、氏名が空。管理画面では空欄で出る |
| 低 | `t_newsletter_subscribers` に保存の期限は無い。個人情報（氏名・アドレス・IP）を持ち続ける。必要なら、`config/cleanup.php` の `tasks` に片付けを足す |

## F. セキュリティ・権限・データ整合性の注意

- 申し込みは、確認コードが通るまで何も保存しない。他人のアドレスを勝手に登録できない。
- 完了の画面と配信停止の画面は、会員かどうかに関係なく同じ表示にし、アドレスの存在を漏らさない。
- 確認コードは、使い道ごとにセッションのキーが分かれ、会員登録など、ほかの画面のコードとは混ざらない。
- 管理画面は、一斉メールと同じく管理者だけ（`EnsureStaffIsManager`）。管理者でないスタッフは、自分の情報の編集の画面へ回される。
- メルマガ希望者の CSV は個人情報なので、ダウンロードの記録（`csv_download_logs`）と操作ログを残す。数式に見える値は無害化する。
- 申し込み・停止は、それぞれ1つのトランザクションで、行と操作ログを一緒に書く。
- メールアドレスの一意は DB の unique で守る。大文字と小文字の違いは、DB の照合順序（大文字・小文字を区別しない）に任せている ※推測（MariaDB の既定の照合順序のため）。
