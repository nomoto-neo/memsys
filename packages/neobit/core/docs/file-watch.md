# 改ざん監視（FileWatcher）

<p align="right"><a href="../guide.md">利用ガイドへ戻る</a></p>

**ファイル**：`packages/neobit/core/src/Security/FileWatcher.php`（冒頭のコメント）・`src/Console/FileWatch.php`、メールは `packages/neobit/core/resources/mail-templates/file_watch_alert.blade.php`

通常の運用では変わらないファイルが変わった・増えた・消えたことと、許可されていないアップロードファイル（`.php`・JavaScript・HTML など）を見つけて、通知のメールで知らせます。入口で止めきれずに書き換えられたとき、侵入者が仕組みに気付く前に知らせるためです。改ざんされたら管理画面を見て運用する状況ではないので、知らせは管理画面ではなくメールで届けます。管理画面の「改ざん監視」は、今の状況を見ることと、知らせた変化を承認するためのものです。

## サーバーの設定（1回だけ。サーバーを管理する人）

コードを更新する利用者（開発サーバーでは devapp、本番では webapp）の crontab に、2行を書きます。Laravel のスケジューラー（apache の cron）には入れません。記録（`bootstrap/cache/file-watch.json`）をその利用者だけが書けるようにし、Web の側から侵入した攻撃者（apache の権限）が書き換えられないようにするためです。

`/etc/cron.d/` に置く例です（root しか書き換えられないので、apache の権限で侵入されても監視を止められません）。`--full` は、5分ごとの回と重ならないよう、5の倍数でない分にします。3行目は、管理画面の「改ざん監視」で承認した変化を、1分以内に取り込むための行です（下の「管理画面の「改ざん監視」」）。無くても、5分ごとの回が先に取り込みます。

```
MAILTO=dev@example.com
*/5 * * * * devapp cd /var/www/memsys_dev && /usr/bin/php artisan neobit:file-watch > /dev/null
32  7 * * * devapp cd /var/www/memsys_dev && /usr/bin/php artisan neobit:file-watch --full > /dev/null
*   * * * * devapp cd /var/www/memsys_dev && /usr/bin/php artisan neobit:file-watch --approve > /dev/null
```

- **エラーの出力は捨てず、`MAILTO` を書きます**。改ざん監視も Laravel の上で動くので、Laravel が動かなくなる改ざんをされると、監視も止まり、メールも送れません。エラーの出力（`2>&1` の分）を捨てずにおけば、コマンドが例外で止まったときに、cron がその出力を `MAILTO` へメールで送ります。Laravel の外（cron とサーバーのメールの送信）で届くので、Laravel が動かなくても知らせが来ます。サーバーからメールを送れる設定が要ります。
- PHP や cron そのものを止められたら、これも届きません。そこは外部の監視サービスの役目です（[security.md](security.md)の「サイトの改ざんを見つける仕組みの重ね方」）。

書いたら、同じ利用者で1回だけ基準を作ります。

```bash
sudo -u devapp /usr/bin/php artisan neobit:file-watch --init
```

5分ほど待ってから同じ利用者で `neobit:file-watch` を手で1回動かし、「改ざんの疑い：0件」と出れば動いています。

## 鍵のファイル（サイトを更新するたび）

- 鍵のファイル（`config/neobit.php` の `file_watch.release_file`。既定はプロジェクトの直下の `.version`）の更新の15分後より前に変わったファイルは、通常のサイトの更新とみなし、知らせずに基準へ取り込みます。
- **サイトを更新するときは、鍵のファイルも送ります**。監視が見るのは鍵の ctime だけなので中身は何でもよいのですが、FTP の同期や `rsync` は中身が同じファイルを送らずに飛ばすので、送るたびに日時などを書いて中身を変えます。サーバーで `touch .version` を実行しても同じです。
- 鍵の時刻は、mtime ではなく ctime（サーバーに届いた時刻）で見ます。SCP（`-p`）・rsync（`-t`・`-a`）・多くの FTP のソフトは、手元のファイルの mtime を写すので、mtime では送った時刻が分からないためです。送る人から見れば、ctime は「`.version` を送った時刻」そのものです。
- **`set_permissions.sh --apply`（[deploy.md](deploy.md)）も、鍵の ctime を新しくします**。権限を直しただけでも、改ざん監視から見ると `.version` を送ったのと同じになり、鍵の15分後より前に変わったファイルが、知らせ中のものも含めて全部、通常の更新として取り込まれます。流す前に、`neobit:file-watch` で「改ざんの疑い」と「判断待ち」が0件であることを確かめます。取り込まれたものは、1日1回の報告に載ります。
- 鍵のファイルは、コードを更新する利用者だけが書ける場所に置きます。
- `php artisan neobit:file-watch` を手で動かすと、通常の更新として取り込む期限（鍵のファイルの更新の15分後）が出ます。鍵のファイルの名前は出しません。
- **git でデプロイするとき**：`git pull` も変わったファイルを書き換えるので、検知できます。ただ、`git pull` は変わったファイルしか書き換えないので、鍵のファイルがそのコミットで変わっていなければ、鍵の ctime が変わりません。デプロイの手順の最後に `touch .version` を1回実行します（`composer install`・`npm run build`・`view:cache` の後。全部の手順が終わってから鍵を更新すれば、手順の間に変わったファイルを全部受けられるため）。コミットのたびに `.version` を書き換える形にするなら、git のフック（`post-merge`）で `touch` するほうが忘れません。`.git/` は監視していません。あわせて、送った後に `git status --porcelain` で git に無い変更が無いことを確かめると、もう1つの確かめになります。

## 通常の更新の見分け方

- 見えた鍵どうしの間が30分以内なら、1つの更新の期間にまとめます。鍵の15分後より前に変わったファイルは、どれだけ前のものでも、通常の更新として取り込みます。知らせ中のファイルも同じです。続けて何度も更新しても、1つの期間になります。
- 判断はファイルごとに、ctime で行います（mtime は `touch -d` で書き換えられるため）。
- 鍵の15分後より後の変化は、そのファイルの ctime から15分たつまで待ちます。送る順番で、鍵が後から届くことがあるためです。たっても鍵が来なければ、改ざんとして知らせます。そのため、知らせるまで最大でおよそ20分かかります。
- 通常の更新とみなしたファイルは、1日1回の操作ログの報告（[operation-log.md](operation-log.md)）に、期間ごとにまとめて載ります。鍵を悪用されても、運営者の目に入るようにするためです。

## 知らせるもの

- 監視する場所の、変わった・増えた・消えたファイル。監視する場所は次のとおりです。`vendor/` は1日1回の `--full` のときだけ見ます。
    - `app/`・`packages/`・`config/`・`routes/`・`bootstrap/`・`database/`・`resources/`・`lang/`・`code/` と、公開ディレクトリ（`public_path()`。`storage` を除く）の全部のファイル
    - プロジェクトの直下の全部のファイル（`.env`・`artisan`・`composer.json` など）。中身まで見ます。`.env` は apache からは読めませんが、監視の利用者は読めます。記録に残すのはハッシュ値だけです
    - コンパイル済みの画面（`bootstrap/cache/views`）。PHP として動くので、コードと同じに見ます。デプロイの `view:cache` で作り直すので、**鍵のファイルは `view:cache` の後に更新します**
    - プロジェクトの直下のディレクトリ。名前が増えた・消えたことだけを見ます（例：知らない `backdoor/` ができた）
    - `bootstrap/cache` の設定などのキャッシュ（`config.php` など）。サーバーの Laravel が実際に読むのは `.env` ではなくここなので、書き換えられるとすぐに効くためです。**デプロイの外で `config:cache` をやり直したとき（`.env` を変えたときなど）は、`.version` も一緒に更新します**
    - 外すのは、この監視の記録とロックのファイル、鍵のファイル、サーバーでテストを動かしたときにできる `.phpunit.cache`・`.phpunit.result.cache` です
- 公開のアップロードの置き場所（`storage/app/public`。`/storage/` の URL で外から開ける）の、許可されていないアップロードファイル。アップロードのたびにファイルが増えるので、基準とは比べずに、毎回次のものを探し、待たずにすぐ知らせます。
    - PHP として動く拡張子のファイル（`.php`・`.phtml`・`.phar` など）
    - アップロードの設定（`neobit.upload.image_types`・`attach_types`）と、`file_watch.public_upload_extra` に無い拡張子のもの。JavaScript・CSS・HTML・SVG などを、一覧に書かずに全部拾います。画面からのアップロードでは置かれ得ないので、あれば改ざんの疑いが強いためです。
- アップロードの置き場所の `.htaccess`・`.user.ini` は、置かれると PHP を動かす設定にされるので、ほかのコードと同じく基準と比べます。増えた・変わった・消えたら、鍵のファイルの期間に入らなければ改ざんとして知らせます。プラグインなどが置く正しいものもあるので、種類の確かめのようにすぐ知らせ続けることはしません。動いている途中でプラグインが作ったものは1回知らせるので、中身を確かめて `--accept` で取り込みます。前の版の基準には入っていないので、新しい版にした最初の回だけは、今あるものを知らせずに取り込みます。
- WordPress を置く案件（[wordpress.md](wordpress.md)）では、WordPress のアップロードの置き場所（設定の `wordpress.upload_path`。見本は `public/wp-content/uploads`）も、`storage/app/public` と同じに扱います。公開ディレクトリの中ですが、`.htaccess`・`.user.ini` のほかは基準と比べず、ファイルの種類だけを確かめます。比べると、画像を上げるたびに追加として知らされるためです。設定の `wordpress.watch_exclude` の場所（キャッシュのプラグインが書く場所など）は、何も見ません。WordPress の本体・プラグイン・テーマは、apache が書けないので、ほかのファイルと同じく基準と比べます。お客さんが画面から更新する案件（[wordpress.md](wordpress.md)）でも同じで、変わったファイルは管理画面の承認で取り込みます。
- `watch_exclude` の場所は、PHP の権限で書けて、中身の書き換えに気付けません。キャッシュのプラグインが書く HTML・JavaScript を書き換えられると、消えるまでそのままページに出ます。キャッシュはどこに置いても（Redis などのメモリでも）PHP から書けるので、改ざん監視では見られません。キャッシュの書き換えに気付くには、外から定期的にページを取得して比べる外部の監視サービスを使います（[security.md](security.md)の「サイトの改ざんを見つける仕組みの重ね方」）。
- 非公開の置き場所（`storage/app/private`）は見ません。Web から直接開けないので置かれても動かせないうえ、Laravel が作った本人（apache）しか読めない権限（0700・0600）で作られ、監視の利用者には開けないためです。
- 監視する場所の中に、監視の利用者が開けないディレクトリがあれば、止まらずに飛ばし、「確かめられなかったディレクトリ」として知らせます。改ざんを隠す場所になり得るためです。その下のファイルは、消えたものとしては扱いません。
- 5分ごとの回と `--full` の回が重ならないよう、記録の隣のロックのファイル（`bootstrap/cache/file-watch.lock`）を押さえます。前の回が動いている間は、次の回は何もせずに終わります。
- 知らせたファイルは基準に取り込まず、直るまで（元の中身に戻るか、通常の更新の期間に入るまで）知らせ続けます。監視が回るたびに（5分ごとに）メールを送ります。改ざんはすぐに対処するものなので、間引きません。送信に失敗しても、次の回に送り直します。
- 宛先は `file_watch.to`、無ければエラーの通知と同じ `ERROR_NOTIFY_TO` です。件名は `【緊急：サイト名】ファイルの改ざんを検知しました（変更 1件・追加 0件・削除 0件）` の形です。

## ファイルの置き場所の使い分け

- **サイトの部品（JavaScript・CSS・HTML・デザインの画像）は、公開ディレクトリに直接置きます**。監視されるので、デザイナーがファイルを置いたり直したりしたときも、鍵のファイルを一緒に送ります。デザイナーにも伝えておきます。
- **運用で入れ替える画像・PDF などは、公開のアップロードの置き場所（`storage/app/public`）の下に、独自のサブディレクトリ（例：`storage/app/public/campaign/`）を作って置けます**。基準とは比べないので、監視とぶつかりません。ただ、そこは PHP-FPM（apache）が書ける場所で、中身を書き換えられても気付けません。サイトの部品をそこに置くと、例えば JavaScript を書き換えられて入力を外へ送る仕掛けを足されても分からないので、置きません。アップロードの設定に無い種類を置くときは、`file_watch.public_upload_extra` に拡張子を足します。
- **アップロードを公開ディレクトリ（`public/uploads` など）に直接保存する作りにはしません**。監視の対象なので、アップロードのたびに改ざんとして知らされます。このフレームワークのアップロードは、`storage/app/public` に保存して `public/storage` のリンクから見せる形です。

## 管理画面の「改ざん監視」

**ファイル**：`packages/neobit/core/src/Http/Controllers/FileWatchController.php`、画面は `packages/neobit/core/resources/views/admin/file_watch/index.blade.php`、メールは `file_watch_approved.blade.php`　**実例**：管理画面の「セキュリティ」の「改ざん監視」

改ざん監視の今の状況を見て、`.version` を書き換える正規のメンテナンスのほかで更新した内容（WordPress の画面からの更新など）を、管理画面から承認できます。

- **画面**：開くたびに、その場でチェックし直して「〇〇〇〇-〇〇-〇〇 〇〇:〇〇:〇〇 現在のチェック状況です。」と出します。改ざんの疑い・判断待ち・許可されていないアップロードファイル・確かめられなかったディレクトリ・最近取り込んだ更新（記録にある8日分。開くとファイルの一覧）を並べます。画面は apache で動くので、記録は書きません。apache が中身を読めないファイル（`.env` など）は、最後の cron の結果を使います。
- **承認**：改ざんの疑いと判断待ちを、まとめて承認します。自分で更新したと分かっていれば、15分の知らせを待たずに承認できます。確かめのモーダルで一覧を見てから「承認する」を押すと、承認の目印（`storage/app/file_watch/approval.json`）を置きます。毎分の cron（`neobit:file-watch --approve`。無ければ5分ごとの回）が拾い、一覧のうち、今も疑いか判断待ちのものだけを基準に取り込みます。押した後に増えた変化と、一覧に無い変化は取り込みません。画面を開いてから押すまでの間に一覧が変わったら、承認せずに「開き直した一覧を確かめてから、承認してください」と出します。画面からは一覧そのものではなく、一覧のしるし（ハッシュ値）を送ります。WordPress の更新のようにファイルが多いと、一覧を送ると PHP が受け取れる数（`max_input_vars`、既定1000）を超えて、黙って一部だけになるためです。
- **承認できないもの**：許可されていないアップロードファイルと、確かめられなかったディレクトリです。ファイルを消すか、権限を直します。
- **記録**：押したときに操作ログ（「改ざん監視の承認」）に一覧を残します。受け付けたことは、取り込まれるまで画面に「○○さんの承認を受け付けました」と出します。画面・確かめのモーダル・操作ログは、承認のメールと同じく「変わったファイル」「増えたファイル」「消えたファイル」の見出しで種類ごとにまとめます。確かめのモーダルと操作ログには全部で20件までを並べ、多いときは「ほか○件」にします。全部の一覧は承認のメールに載せます。取り込んだときに「○○さんがサイトの変更内容を承認しました」のメールを、知らせと同じ宛先へ送ります（取り込んだファイルの一覧つき）。1日1回の報告と画面には「○○さんが承認した更新」と出します。承認した覚えが無いのにメールが届いたら、侵入を疑います。
- **二段階認証などは付けていません**：apache の権限で侵入した攻撃者は目印を真似できますが、apache はコードに書けないので、取り込ませられるのはアップロードの置き場所の `.htaccess` くらいです。それも承認のメールと翌日の報告に残るので、記録で気付ける形にしています。
- **ルート**：案件が書きます。管理者だけのグループの中に、`Neobit\Core\Routing\FrameworkRoutes` の1行を書きます。

    ```php
    // routes/admin.php（管理者だけのグループの中）
    FrameworkRoutes::fileWatch('/file-watch');
    ```

## 知らせが来たとき

- サイトの更新をしていたのに知らせが来たら、鍵のファイルを送り忘れています。知らせたファイルが全部自分の更新だと確かめてから鍵のファイルを送ると、消えたファイルも含めて通常の更新として取り込まれ、知らせが止まります。
- 管理画面の「改ざん監視」で承認しても取り込めます。サーバーに入れる人は、監視の利用者で `--accept` を実行しても取り込めます。そのとき知らせるファイルの一覧が出るので、自分の更新だと確かめて `yes` と答えると、基準に取り込みます。取り込んだものは、1日1回の報告に「サーバーで認めた更新」として載ります。

```bash
sudo -u devapp /usr/bin/php artisan neobit:file-watch --accept
```

- `--accept` は、待っている最中の変化（15分たっていないもの）と、許可されていないアップロードファイル・確かめられなかったディレクトリは取り込みません。後の2つは、ファイルを消すか権限を直すまで知らせ続けます。
- `--init` でも基準を作り直せますが、待っている最中の変化まで黙って取り込み、通常の更新の記録も消えます。基準の作り直しは、最初の1回か、監視の場所を変えたときだけにします。
- 更新をしていないなら、サーバーへの侵入を疑います。取り込む前に、変わったファイルの中身とログを確かめます。知らせの原因を確かめ終わるまで、鍵のファイルを送りません。送ると、確かめていないファイルも基準に取り込まれます。

## 限界

- サーバーそのもの（root）を乗っ取られたら、同じサーバーの上の監視は信用できません。外から定期的にページを取得して比べる、外部の監視サービスと組み合わせます。
- 共用のレンタルサーバーで、Web とファイルの更新が同じ利用者で動くときは、記録を Web の側から書き換えられない守りが効きません（[security.md](security.md)の「Laravel を公開ディレクトリの外に置けないサーバー」）。
- DB の中身（記事の本文に仕込まれたスクリプトなど）は見ません。
