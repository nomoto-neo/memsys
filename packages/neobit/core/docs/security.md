# フレームワーク外で考慮すべきセキュリティ対策

<p align="right"><a href="../guide.md">利用ガイドへ戻る</a></p>

フレームワークのプログラムだけでは守れず、サイトごとに、サーバー・DNS・運用の側で決めておくことをまとめます。サイトを公開する前に、どれも確かめます。

| 対策 | 決める場所 | 放っておくと |
|---|---|---|
| パッケージの脆弱性の確認 | デプロイの手順・GitHub | 既知の穴が残ったまま動き続ける |
| 送信元の認証（SPF・DKIM・DMARC） | 送信に使うドメインの DNS | メールが迷惑メールに入る、届かない |
| バックアップと、戻す手順 | サーバー・運用 | 壊れたときに戻せない |
| 外部へ送っている情報の表示 | プライバシーポリシー | 外部送信規律に合わない |

## パッケージの脆弱性の確認

フレームワークは、Laravel をはじめ多くのパッケージの上で動いています。パッケージに脆弱性が見つかると、こちらのプログラムに誤りが無くても、攻撃の入口になります。

- **デプロイの前に調べる**：手元で次の2つを実行し、報告があれば版を上げます。

  ```bash
  composer audit
  npm audit
  ```

- **見つかったときに知らせてもらう**：GitHub のリポジトリの設定で、Dependabot の通知（Dependabot alerts）を有効にします。脆弱性が公表されると、メールで届きます。
- **版を上げるとき**：`composer update`・`npm update` は、動作を確かめてからサーバーへ送ります。サーバーの上では `composer install --no-dev`・`npm ci` だけを実行し、版を上げる操作はしません（[deploy.md](deploy.md)）。

## 送信元の認証（SPF・DKIM・DMARC）

メールを受け取る側は、「そのドメインから送ってよいサーバーか」を DNS で確かめます。設定が無いと、確認コードやお知らせのメール、一斉メール（[queue.md](queue.md)）が、迷惑メールに入ったり、届かなかったりします。大量に送る相手に、この設定を必須にしているメールのサービスもあります。

| 設定 | 中身 |
|---|---|
| SPF | そのドメインのメールを送ってよいサーバーの一覧 |
| DKIM | メールに付ける署名。途中で書き換えられていないことを示す |
| DMARC | SPF と DKIM に通らなかったメールを、受け取る側にどう扱ってほしいか |

- 確かめるのは、`.env` の `MAIL_FROM_ADDRESS` に書いたアドレスのドメインです。`MAIL_RETURN_PATH`（[mail.md](mail.md)）を書いたときは、SPF はそのアドレスのドメインで確かめられるので、同じドメインにします。
- レンタルサーバーの SMTP から送るときは、そのサーバーの管理画面で SPF と DKIM を有効にします。DMARC は、DNS に自分で1行足します。
- サーバーの sendmail（Postfix）から直接送ると、送信元がサーバーの IP アドレスになり、SPF に通らないことがあります。レンタルサーバーの SMTP へ転送する設定にします。
- 設定の後、Gmail などに1通送り、メールのヘッダーに `spf=pass`・`dkim=pass`・`dmarc=pass` と出ることを確かめます。

## バックアップと、戻す手順

ランサムウェア、操作の誤り、サーバーの故障に備えます。取るだけでなく、戻せることを確かめておきます。

- **取るもの**
  - DB の全部
  - アップロードしたファイル（`storage/app`）
  - `.env`。特に `APP_KEY` が無いと、暗号化して保存した列（2段階認証の秘密鍵など）を戻しても読めません。DB のバックアップとは別の場所に控えます
- **置き場所**：サーバーの外に置きます。同じサーバーの中だけに置くと、サーバーごと失われます。
- **残す世代**：何日分を残すかを決めます。壊れたことに気付くのが遅れても、壊れる前まで戻れる長さにします。
- **戻す手順**：手順を書いて、一度は実際に戻してみます。戻した先で、ログインできること、アップロードしたファイルが開けることまで確かめます。
- **個人情報の扱い**：バックアップにも個人情報が入っています。置き場所に入れる人を絞り、残す期間を過ぎたものは消します。

## Laravel を公開ディレクトリの外に置けないサーバー

Laravel は、公開ディレクトリ（Apache の `DocumentRoot`）を `public/` にし、本体（`app`・`config`・`vendor`・`storage`・`.env` など）を公開ディレクトリの外に置く前提で作られています。レンタルサーバーで公開ディレクトリを選べないときは、次の順に考えます。

**A. 公開ディレクトリの外に置く（おすすめ）**

- 多くのレンタルサーバーは、公開ディレクトリ（`public_html` など）の外にもファイルを置けます。「置けない」と思われているサーバーでも置けることが多いので、まずそれを確かめます。
- Laravel 一式を `~/memsys/` に置き、`public_html` を `~/memsys/public` へのシンボリックリンクにします。リンクを作れなければ、`public` の中身を `public_html` に置き、`index.php` の中の Laravel 本体へのパスを `~/memsys/…` に書き換えます。

**B. 公開ディレクトリの中に置くしかないとき**

公開ディレクトリを Laravel の `public` そのものにし、本体だけを公開ディレクトリの `app/system/` に置きます。公開ディレクトリの直下に増えるシステムのディレクトリを `app/` の1つにし、デザイナーが Laravel の外のファイル（HTML・画像など）を公開ディレクトリに自由に置けるようにするためです。Laravel の `.htaccess` は、デザイナーが置いた画像・CSS・JS はそのまま返し、HTML と古い PHP は Laravel を通してから返します（[public-files.md](public-files.md)）。管理画面の既定の URL（`/app/admin`）も、同じ `app/` の下にまとまります。

```
public_html/              ← 公開ディレクトリ。Laravel の public の中身を直接置く
├─ index.php              ← 本体を app/system/ から読むように書き換える
├─ .htaccess              ← Laravel の public/.htaccess ＋ 本体を閉じる1行
├─ build/                 ← npm run build の出力
├─ storage/               ← アップロードの公開分（storage:link）
├─ （デザイナーが置くファイル）
└─ app/
    └─ system/            ← Laravel 本体。外からは閉じる
```

- **`index.php`**：`vendor/autoload.php` と `bootstrap/app.php` の読み込み先を `__DIR__.'/app/system/…'` にし、`$app->usePublicPath(__DIR__);` を足します。`asset()`・アップロードの URL・`public_path()`・`storage:link` の場所を、公開ディレクトリにするためです。最後の行は、見本のサイトの `public/index.php` と同じく `PublicFiles::handle()` にします（[public-files.md](public-files.md)）。頭の入口の見張り（[ip-block.md](ip-block.md)）も、`NEOBIT_GATEKEEPER_STATE` と `gatekeeper.php` の読み込み先を `__DIR__.'/app/system/…'` にします。
- **`vite.config.js`**：`npm run build` の出力先（`laravel()` の `publicDirectory`）を公開ディレクトリにします。
- **本体を閉じる（守りを2枚にする）**：公開ディレクトリの `.htaccess` の `RewriteEngine On` の次に、`/app/system/` の下は 404 を返す1行を足します。403 だと、そこに何かあることを教えるためです。加えて `app/system/.htaccess` に `Require all denied` を置き、`.htaccess` の書き損じでも本体が見えないようにします。

    ```apache
    RewriteRule ^app/system(/|$) - [R=404,L]
    ```
- **`app/` には `.htaccess` を置きません**。置くと、`/app/admin` が Laravel に届かなくなります。
- **置いた後に、外から確かめます**：`/app/system/.env`・`/app/system/storage/logs/laravel.log`・`/app/system/vendor/composer/installed.json` などが、どれも 404 になること（`docs/security-external-check.md` の5）。
- **自衛の機能への影響**：共用のサーバーは、Web とファイルの更新が同じ利用者で動くことが多いので、改ざん監視の「基準を Web の側から書き換えられない」守りが効きません。外から監視するサービスと組み合わせます。VirtualHost に書けないサーバーでは、ベーシック認証の決まり（[basic-auth.md](basic-auth.md)）を公開ディレクトリの `.htaccess` に書きます。
- 見本のサイトのリポジトリの形（`public/`）は変えません。この置き方は、サーバーに置くときだけのものです。

## サイトの改ざんを見つける仕組みの重ね方

改ざん監視（[file-watch.md](file-watch.md)）は、サーバーの外の仕組みや root の権限に頼らず、フレームワークの側だけで行う自衛です。ほかの方法と重ねると、見落としが減ります。

| 方法 | 中身 | 今回の改ざん監視との違い |
|---|---|---|
| フレームワークの改ざん監視（[file-watch.md](file-watch.md)） | ファイルのハッシュ値を基準と比べる。鍵のファイルで通常の更新を見分ける | root の権限が要らず、レンタルサーバーでも動く。サーバー全体（root）を乗っ取られると信用できない |
| サーバーの改ざん検知のソフト（AIDE・Tripwire・Wazuh など） | root で、サーバー全体のファイルのハッシュ値・権限・持ち主を基準と比べる。基準は書き換えられない場所に置く | サーバー全体（`/etc`・`/usr/bin` など）を見られる。root を持てる VPS 向け。サイトの更新のたびに基準を作り直す運用が要る |
| その場で捕まえる（inotify・auditd） | 書き込みが起きた瞬間に知らせる | 知らせが速い。サーバーの設定と root の権限が要る |
| 外部の監視サービス | 外から定期的にページを取得し、中身の変化・知らないスクリプトの埋め込み・マルウェアの配布・ブラックリストへの掲載を調べる | サーバーの中の監視が乗っ取られても、外からは見える。見るのは外から見える部分だけで、表に出てから気付く |
| 書き換えられない作り | コードのディレクトリを Web の権限から読むだけにする。git や CI から送り、サーバーで直接ファイルを触らない | 改ざんを起こしにくくする。改ざん監視の記録を守る前提でもある |

- **重ね方のおすすめ**：フレームワークの改ざん監視に、外部の監視サービスを1つ足すのが、いちばん効きます。root を持てる VPS では、AIDE などでサーバー全体も見張ります。
- WordPress のプラグイン（Wordfence など）のように、Web の権限で動く監視は、乗っ取られると監視ごと無効にされます。改ざん監視の cron を apache ではなく、コードを更新する利用者で動かすのは、この弱点を避けるためです。

## 外部へ送っている情報の表示

訪問者のブラウザから、こちらのサーバーのほかにも、情報が送られています。外部送信規律（電気通信事業法）は、どこへ・何を・何のために送っているかを、訪問者に示すことを求めています。

フレームワークの部品が外部へ送るものは、次のとおりです。使っていない部品の分は、載せなくて構いません。

| 送り先 | 送るもの | 使っている所 | 目的 |
|---|---|---|---|
| jsDelivr（CDN） | IP アドレス、ブラウザの情報 | 全部の画面（Bootstrap・jQuery の読み込み。管理画面は Bootstrap Icons も） | 画面の表示 |
| Cloudflare（Turnstile） | IP アドレス、ブラウザの情報 | お問い合わせなどの訪問者向けフォーム（[public-form.md](public-form.md)） | 機械による送信の判定 |
| zipcloud | 入力した郵便番号、IP アドレス | お問い合わせの住所の入力 | 郵便番号からの住所の検索 |

- この一覧を、プライバシーポリシーか、そこからたどれるページに載せます。
- 外部のサービスを足したとき（アクセス解析、地図、広告など）は、この一覧にも足します。
